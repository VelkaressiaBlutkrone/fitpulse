# FitPulse 제품 구축 단계 전환 계획 (2026-08-17)

Status: DRAFT — 소유자 검토 대기

Applies to: `ADR-20260814-002` 대체와 `PRODUCT_BUILD` 단계 도입

## 이 문서의 목적

`ADR-20260814-002`(랜딩 우선 사전 검증)가 회원 계정·인증·건강데이터·개인화를 현재 단계의 제외 범위로 두고 있어 제품 기능 개발을 착수할 수 없다. 이 계획은 그 결정을 대체할 새 ADR의 내용과, 함께 갱신해야 할 문서를 확정한다.

이 문서는 **설계 확정본**이며 구현 계획이 아니다. 실제 작업 분할은 이 문서 승인 후 TASK-0005의 Workflow로 만든다.

## 소유자 결정 사항 (2026-08-17)

이 계획의 모든 방향은 아래 네 결정에서 나왔다. 대안과 그 대가를 제시한 뒤 소유자가 선택했다.

| # | 질문 | 결정 | 제시했던 대안 |
|---|---|---|---|
| 1 | MVP에서 열려는 범위 | **wiki v2 전체 범위** | 계정 없는 로컬 전용 앱 / 계정·서버 동기화까지 |
| 2 | 랜딩과 사전검증의 처리 | **대기자 모집으로 유지, 제품은 병렬 착수** | 랜딩 공개를 선행 조건으로 / 사전검증 종료 |
| 3 | ADR 갱신 방식 | **새 ADR로 대체** | 능력별 게이트로 개정 / 제외 범위만 해제 |
| 4 | 구축·운영 예산 | **공백으로 두고 G1 착수 전 결정** | 지금 금액 확정 |

### 결정 1에 대해 기록해 두는 우려

wiki v2 전체 범위를 선택하면 `ADR-20260814-002`의 재개 조건 5개가 사실상 동시에 발동하고, 랜딩이 아직 공개되지 않아 **수요 데이터 없이 대규모 구축에 들어간다.** 이 우려를 선택 시점에 제시했고 소유자가 그대로 선택했다. 감추지 않고 새 ADR 본문에도 기록한다.

## 배경 — 현재 저장소의 사실

실측으로 확인한 것만 적는다.

- 최상위 디렉터리는 `docs/`, `landing/`, `wiki/`뿐이다. **백엔드·앱·관리자 웹 코드는 존재하지 않는다.**
- `CLAUDE.md`의 빌드·테스트 절이 `./gradlew test`, `flutter analyze`, `flutter test`, `npm run build`를 적어두고 있으나 그 대상 모듈이 없다. 같은 절이 "실제 모듈 경로와 빌드 설정 파일을 읽어 해당 명령이 현재 저장소에 적용되는지 확인한다"고 단서를 달고 있다.
- `wiki/README.md` 3행이 wiki를 "공개 역사 자료"로 규정하고 "최신 실행 기준과 결정은 `docs/`를 따릅니다"라고 명시한다.
- wiki v2 배포가이드가 전제하는 스택은 Spring Boot(`./gradlew`), MySQL, Redis, Flutter 3.47 stable, React 관리자 웹(`npm run build`)이다.
- 랜딩은 `develop`에 병합되어 있으나 **소유자 전용이며 공개된 적이 없다.** 공개 판정은 `TASK-0004`에 `Draft`로 있고, Worker 시크릿 주입 경로 미확인으로 막혀 있다.
- `ADR-20260814-001`의 500,000원은 `ADR-20260814-002` 25행이 "전체 검증 예산 상한"으로 규정한 값이다.

## O-1. 새 ADR의 내용

### 번호를 005로 하는 이유

`TASK-0004`의 `WF-02`가 산출물로 `ADR-20260817-004-landing-public-release-decision.md`를 이미 예약했다. 004를 가져가면 그 문서를 고쳐야 하므로 예약을 존중한다. ADR-005 본문에 "004는 랜딩 공개 판정용으로 예약됨"을 적어 빈 번호가 누락으로 보이지 않게 한다.

### 단계 이름: `PRODUCT_BUILD`

`MVP_BUILD`로 쓰지 않는다. 선택된 범위는 요구사항 136건, ERD 43테이블, 관리자 웹 RBAC 5역할×27권한을 포함하며 최소 기능 제품이 아니다. `CLAUDE.md` 절대 조건 5(검증되지 않은 성공을 보고하지 않는다)의 취지를 단계 이름에도 적용한다.

### 포함할 절

**1. 결정** — 현재 단계를 `PREVALIDATION_LITE`에서 `PRODUCT_BUILD`로 전환한다. `ADR-20260814-002`를 대체한다.

**2. 범위** — wiki v2 문서 세트를 **범위 정의의 입력**으로 채택한다. 실행 기준으로 승격하지 않는다.

> wiki v2의 요구사항·ERD·API 명세는 각 하위 프로젝트 착수 시 그 시점의 사실로 재검토한 뒤 `docs/`에 실행본을 만든다. `wiki/`는 계속 역사 자료이며 실행 기준이 아니다.

이 방식을 택한 이유는 두 가지다. wiki v2는 2026-08-13 기준이라 그 뒤 확인된 사실(데이터 레지던시 미지원, 예약 작업 미지원, 플랫폼 프로비저닝 D1 등)을 반영하지 못한다. 그리고 전면 승격하면 `wiki/README.md` 3행과 정면으로 충돌해 그 파일까지 고쳐야 한다. 입력으로 두면 두 문제가 함께 해소된다.

**3. 스택과 저장소 구조**

| 모듈 | 스택 | 경로 |
|---|---|---|
| 백엔드 | Spring Boot, MySQL, Redis | `backend/` |
| 모바일 앱 | Flutter 3.47 stable | `app/` |
| 관리자 웹 | React | `admin/` |
| 랜딩 | 기존 유지 | `landing/` |

**4. 구축 순서**

```
1. 백엔드 코어      계정·인증 + 운동 기록 CRUD
2. 앱 코어          기록 입력 + 다음 증량 제안
3. 개인화 심화      루틴·회복 반영
4. 관리자 웹        운영 필요가 실제로 생긴 뒤
5. 공개 베타·출시
```

2번까지가 제품 가설("지난 수행 기반 증량 제안이 쓸모 있는가")에 답한다. 4번은 사용자가 있어야 의미가 생기므로 뒤에 둔다. 각 단계는 별도 TASK로 분할하며 이 ADR은 순서와 게이트만 정한다.

**5. 게이트** — `ADR-20260814-002`의 재개 조건을 폐기하지 않고 시점과 산출물로 구체화한다.

| 게이트 | 발동 시점 | 착수 전 필수 산출물 |
|---|---|---|
| G1 회원 계정·인증 | 구축 1단계 | 개인정보 처리방침(수집·보유·삭제·수탁), 보안 설계(인증·세션·비밀번호·2FA), 계정 복구·탈퇴 운영 절차, 구축·운영 예산 상한 결정 |
| G2 개인화된 운동 조정 | 구축 3단계 | 안전 고지와 책임 한계, 제안 알고리즘 설명, 부적합 사용자 배제 기준 |
| G3 건강·웨어러블 데이터 | Health Connect 도입 시 | 민감정보 처리 근거, 별도 동의 설계, 영향평가 수준 검토 |
| G4 결제·환불 | 구축 5단계 | 결제대행 계약, 환불 정책, 세금·정산 처리, 예산 재검토 |
| G5 공개 베타·앱스토어 | 구축 5단계 | 출시 문서, 스토어 정책 대응, 운영 매뉴얼, 장애 대응 절차 |

절차는 모든 게이트에 동일하다.

```
문서 작성 → 소유자 검토 → 판정을 TASK/HISTORY에 기록 → 착수
```

게이트를 통과하지 않은 능력은 구현하지 않는다.

G1을 구축 1단계에 둔 것은 의도한 배치다. 계정·인증이 첫 모듈이므로 제품 트랙의 개인정보·보안 기준이 코드보다 먼저 정해진다.

**6. 랜딩 트랙** — `ADR-20260814-002`의 최소 운영 기준 6개를 **전문 그대로 옮겨 적는다.** 참조가 아니라 본문으로 옮긴다.

- 아직 개발 전 검증 단계임을 숨기지 않는다.
- 이메일 저장소와 행동 이벤트 저장소를 논리적으로 분리한다.
- URL, 분석 이벤트, 애플리케이션 로그에 이메일을 넣지 않는다.
- 실제 저장·분석 공급자, 수집 항목, 목적, 보유 기간, 삭제 요청 방법을 공개 시점의 개인정보 안내에 적는다.
- 동의하지 않거나 철회한 사람의 등록·삭제 흐름을 실제로 시험한다.
- 랜딩 반응은 수요 신호로만 보고 제품 적합성·결제 의사·법적 적합성으로 과장하지 않는다.

옮겨 적는 이유는 `ADR-20260814-002`가 `SUPERSEDED`가 되기 때문이다. 죽은 문서에 살아있는 규칙을 두면 다음 작업자가 "대체된 문서니 안 지켜도 되는가"를 매번 판단하게 된다. 규칙이 두 곳에서 다르게 진화하는 것도 막는다.

랜딩 공개(`TASK-0004`)는 제품 개발의 선행 조건이 아니다. 제품 개발을 랜딩 지표에 종속시키지 않는다.

**7. 예산** — 금액을 적지 않는다.

> 500,000원 상한은 검증 예산이며 구축·운영 비용을 포함하지 않는다. 구축·운영 예산 상한은 **미정**이며, G1 착수 전에 소유자가 결정해 이 ADR에 추가한다. 결정 전까지 상시 비용이 발생하는 인프라를 프로비저닝하지 않는다.

확인하지 않은 수치를 문서에 넣지 않는다(`CLAUDE.md` 절대 조건 1). 예상되는 비용 항목은 성격만 기록한다: 서버·MySQL·Redis 호스팅(상시·사용량 비례), 도메인·인증서(연간), 스토어 등록비(1회 또는 연간), 이메일 발송(사용량 비례).

**8. 보증 수준** — `ADR-20260814-001`의 `SOLE_PROPRIETOR_SELF_REVIEW`를 변경하지 않는다. 다만 한계를 명시한다.

> 계정과 개인정보를 다루는 제품에서 한 사람이 설계·구현·개인정보 검토·게이트 판정을 모두 수행한다. 독립 검증을 받은 것으로 주장하지 않는다.

이 한계는 G1·G3 산출물에도 반복 기록한다.

**9. 이 결정의 한계** — 결정 1의 우려를 본문에 남긴다.

> 이 단계 전환은 랜딩 수요 데이터가 확보되기 전에 이뤄졌다. 랜딩은 구현되었으나 공개된 적이 없고 기준선 지표가 없다. 따라서 구축 범위의 크기는 확인된 수요가 아니라 소유자의 판단에 근거한다.

## O-4. `CLAUDE.md` 변경

빌드·테스트 절이 존재하지 않는 모듈의 명령을 나열하고 있다. 다음으로 정정한다.

- 현재 존재하는 모듈은 `landing/`뿐이며 검증 명령은 `npm test`, `npm run lint`, `npm audit --omit=dev --audit-level=high`임을 명시

- Wiki 배포가이드의 명령은 참고 자료이며 현재 저장소에 적용되지 않는다는 사실 명시

- wiki v2 요구사항·ERD·API의 실행본 작성 — 각 하위 프로젝트 착수 시
- G1~G5 게이트 산출물의 실제 작성 — 각 게이트 도달 시
- 구축·운영 예산 금액 결정 — 소유자, G1 착수 전
- 랜딩 공개 판정과 기준선 계측 — `TASK-0004`
- `wiki/` 문서 수정 — 역사 자료로 유지

## 위험

- **수요 근거 없는 구축 규모.** 랜딩이 공개되지 않아 기준선이 없다. 구축 범위가 확인된 수요가 아니라 판단에 근거한다. ADR-005 본문에 명시한다.
- **예산 공백 중 인프라 프로비저닝.** 상한이 미정인 상태에서 MySQL·Redis를 띄우면 통제 없는 상시 비용이 발생한다. ADR-005에 "결정 전까지 상시 비용 인프라를 프로비저닝하지 않는다"를 넣어 막는다.
- **낡은 설계의 무검증 유입.** wiki v2는 2026-08-13 기준이며 그 뒤 확인된 사실을 반영하지 못한다. "범위 정의의 입력"으로 격하하고 착수 시 재검토를 요구해 막는다.
- **게이트 우회.** 구현 중 편의상 게이트를 건너뛸 유인이 생긴다. 게이트 판정을 TASK/HISTORY 기록 의무로 걸어 흔적이 남게 한다.
- **1인 자체 검토의 한계.** 계정·개인정보를 다루는 제품에서 설계·구현·검토·판정을 한 사람이 수행한다. 해소할 수 없는 구조적 한계이므로 주장 제한으로 관리한다.
- **문서 규모 증가.** 게이트 5개의 산출물이 누적되면 문서 관리 부담이 커진다. 각 게이트를 해당 구축 단계 직전으로 분산해 완화하나 총량은 줄지 않는다.
