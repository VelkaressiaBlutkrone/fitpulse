## Proposed Direction

Office Hours에서는 증거 게이트형 단계별 프로그램인 Approach C를 선택했다. 이 선택은 장기 기능군이나 18주 구현을 승인한 것이 아니다. 모바일 앱, 서버, Health Connect, AI, 커뮤니티와 관리자 기능은 모두 **폐기 가능한 가설 백로그**로 남긴다. 실제 사용자, 현재 대안, 손실, 차별화, 리텐션, 지불 구조, 규제 경로, 경제적 내부 후원자와 구현 저장소가 확인되기 전에는 제품 코드를 시작하지 않는다.

제안된 프로그램은 다음 순서로만 진행한다.

`G-1 위임·책임자 부트스트랩 → G0A 최소 권위·안전 감사 → G1 문제·시장·후원자 증거 → G2A 사용성 검증 → G2B 수작업 가치·리텐션·수익성 검증 → G0B 선택 범위 정합성 → G3 규제·경제성·구현 준비 → G4 통제된 수직 슬라이스 → G5 제한 운영 파일럿 → G6 증거 기반 확장`

각 게이트의 결과는 `GO`, `LOOP`, `STOP` 중 하나로 기록한다. 앞 게이트를 통과하지 않은 상태에서 다음 단계의 일정이나 기능을 확정하지 않는다. `DRAFT` 상태에서는 아래 규칙도 제안일 뿐이며, 문서 승인 시에만 프로그램 규칙이 된다.

## Evidence Labels

이 문서에서는 사실과 계획을 섞지 않기 위해 다음 표기를 사용한다.

- **확인됨**: 저장소 파일, 실행한 명령 또는 사용자의 명시적 답변으로 확인한 내용
- **외부 근거**: 1차 출처 또는 연구 원문에서 확인했으며 출처와 확인일을 기록한 내용
- **제안됨**: 이 문서가 새로 정의하는 운영 규칙 또는 통과 기준
- **미확인**: Wiki에는 있으나 현재 저장소나 실제 사용자에게서 검증하지 못한 내용
- **차단**: 다음 게이트로 가기 전에 반드시 해결해야 하는 조건

## Problem Statement

**확인됨:** Wiki는 Flutter 모바일 앱, Spring Boot 서버, 오프라인 동기화, Health Connect, AI 루틴, 분석, 커뮤니티와 관리자 기능을 하나의 18주 프로그램으로 설명한다. 기능과 기술 설계는 상세하지만, 이번 Office Hours에서 다음 세 가지 수요 근거는 모두 없다고 답변했다.

1. 제품이 사라지면 곤란해할 실제 사용자 또는 사용 행동
2. 사용자가 지금 수행하는 구체적인 대체 업무와 그 비용
3. 가장 절실한 실제 사람, 직무, 책임과 실패 결과

**확인됨:** 현재 저장소에서 표준 애플리케이션 소스 확장자(`java`, `kt`, `kts`, `dart`, `js`, `jsx`, `ts`, `tsx`, `py`, `go`, `rs`, `swift`, `cs`, `sql`)를 검색한 결과는 0개이며, `gradlew`, Gradle 설정, `pubspec.yaml`, `package.json`, Docker Compose 같은 빌드·실행 설정도 없다. 이 검색은 비표준 확장자나 다른 저장소의 소스 부재까지 증명하지 않는다. 따라서 Wiki 작업로그의 Flutter 스캐폴딩 및 Docker Compose 진행 표시는 현재 저장소에서 검증되지 않는다.

**외부 근거:** Strong 공식 도움말은 무료 사용자의 운동 기록을 계속 허용하고, Hevy 공식 가격표는 무료 플랜의 무제한 운동 기록을 명시한다. Hevy 기능 문서는 세트·RPE·휴식 타이머와 오프라인 기록을 설명한다. 다만 Strong 무료는 저장 템플릿 3개, Hevy 무료는 루틴 4개·커스텀 운동 7개·통계 이력 3개월 제한이 있어 “FitPulse MVP 전체가 경쟁사의 무료 티어에 모두 포함된다”는 문장은 사실보다 넓다. 더 정확한 결론은 **핵심 기록 기능만으로는 이미 성숙한 무료 대안과 구별되지 않는다**는 것이다.

**제안됨:** Operation Queue, Conflict Matrix와 Change Token 처리는 출시 품질과 신뢰의 기반이지 독립적인 구매 이유로 간주하지 않는다. 지불 의사는 사용자가 얻는 결과와 전환 이유로 별도 검증한다.

따라서 지금 해결할 문제는 “Wiki에 적힌 모든 기능을 어떻게 구현할 것인가”가 아니다. 먼저 “어떤 실제 사람이 어떤 반복 문제를 겪고, 기존 무료 대안에서 왜 전환하며, 어떤 반복 결과에 돈이나 조직 예산을 지불할 것인가”를 확인해야 한다. 그렇지 않으면 상세한 아키텍처가 검증되지 않은 가설을 더 비싸게 고정한다.

## Demand Evidence

| 항목 | 현재 상태 | 다음 증거 |
|---|---|---|
| 실제 수요 행동 | 없음 | 사용자가 현재 해결책에 시간·비용을 쓰거나 문제 때문에 업무 결과를 잃는 관찰 기록 |
| 현재 대안 | 없음 | 도구, 사람, 수기 절차와 단계별 소요 시간·오류·빈도 |
| 구체적 사용자 | 없음 | 이름 또는 내부 식별자, 역할, 책임, 문제의 실제 결과 |
| 경제적 내부 후원자 | 없음 | 문제 비용과 예산에 책임지고 시간·데이터 접근과 `GO/STOP`을 결정할 사람 |
| 제품 성과 기준선 | 없음 | 현재 업무의 빈도, 시간, 실패율 또는 결과값 |
| 경쟁 전환 이유 | 없음 | Strong·Hevy 등 실제 대안에서 바꿀 관찰 가능한 이유 |
| 리텐션 메커니즘 | 없음 | 스트릭이 아니라 반복 업무 결과 때문에 다시 사용하는 행동 |
| 지불·단위 경제 | 없음 | 가격 수용 증거와 사용량별 공헌이익 모델 |
| 배포·규제 경로 | 없음 | 공개 Play, 관리형 비공개 배포 등 실제 채널과 적용 의무 |

Wiki의 “오프라인 기록 유실 약 8%”, “세트 입력 4~6탭”, “AI 미매핑 15~30%”는 출처와 측정 방법이 문서에 제시되지 않았다. 이 수치는 **미확인 가설**로만 사용하며 제품 목표의 기준선으로 인용하지 않는다.

**외부 근거:** 2024년 18개 연구·525,824명을 포함한 스코핑 리뷰는 다수 연구에서 첫 100일 안에 절반 이상이 앱 사용을 중단했고, 중앙 이탈률이 약 70%였다고 보고했다. 2026년 단일 피트니스 앱 사용자 2,771명 분석에서는 첫 달 훈련 활동이 69.3% 감소했고, 유료 사용자 유지 기간 평균은 153.53일, 무료 사용자는 80.73일이었다. 후자는 단면 관찰 연구이므로 “결제가 리텐션을 만든다”는 인과로 해석하지 않는다.

**외부 근거:** 외부 연구 역시 일반적인 웰니스 앱 도입이 곧 조직 성과로 이어진다고 보장하지 않는다. 2026년 개인화 앱 무작위시험은 운동 시간에 제한적인 개선을 보고했고, 대규모 직장 웰니스 무작위시험들은 측정된 건강·의료 이용·생산성 결과에서 유의한 개선을 확인하지 못했다. 이는 FitPulse가 효과가 없다는 뜻이 아니라, 이 조직과 사용자의 기준선과 반복 사용을 직접 측정해야 한다는 뜻이다.

## Status Quo

현재 사용자의 실제 대체 업무는 확인되지 않았다. 다음 항목은 Wiki와 경쟁 제품에서 추출한 관찰 후보일 뿐 현재 상태의 사실이 아니다.

| 후보 문제 | 관찰해야 할 현재 행동 | Wiki가 제안한 해결책 |
|---|---|---|
| 운동 중 기록 조작 부담 | 세트 기록 시 실제 화면 전환·탭·중단 | 1탭 입력과 낙관적 갱신 |
| 네트워크 불안정 시 기록 손실 | 연결 끊김, 앱 종료, 재접속 과정 | 영속 Operation Queue |
| 건강 데이터 수기 입력 | 입력 빈도, 누락, 재입력 시간 | Health Connect 동기화 |
| 루틴 구성 부담 | 현재 루틴을 찾고 수정하는 절차 | 규칙 검증을 포함한 AI 루틴 |
| 루틴 공유와 신뢰 | 공유 경로, 위험 콘텐츠, 신고 처리 | 심사·좋아요·랭킹·신고 |
| 운영 업무 | 회원·콘텐츠·AI 운영의 실제 건수 | 관리자 RBAC·감사·운영 도구 |
| 기존 무료 로거 | 실제 사용 기능, 유료 제한, 전환 불만 | 차별화된 사용자 결과 |

`G1` 전에는 어느 후보도 우선순위가 아니다.

## Target User & Narrowest Wedge

대상 사용자는 아직 정하지 않는다. “직원”과 “Android 사용자”도 확정된 대상이 아니라 내부 프로젝트에서 모집 가능한 후보 경계다. `G1`이 다음을 모두 산출해야 한다.

- 한 명 이상의 명시된 주 사용자와 그 역할
- 주 사용자가 반복하는 현재 업무의 시작·종료 조건
- 현재 업무가 실패할 때 생기는 구체적 결과
- 해당 결과와 예산에 책임을 지고 파일럿을 승인할 경제적 내부 후원자

최초 웨지는 특정 기능이 아니라 **한 사용자의 한 반복 업무에서 한 결과를 개선하는 수직 단위**다. 후보 웨지는 관찰 후 다음 기준으로 비교한다.

1. 관찰된 빈도와 손실
2. 사용자가 이미 투입하는 시간·비용·도구
3. 결과를 한 파일럿 기간 안에 측정할 수 있는지
4. 건강정보·외부 API·기기 권한 없이도 먼저 검증할 수 있는지
5. 후원자가 성공과 중단을 판정할 수 있는지

Wiki의 오프라인 기록, Health Connect, AI, 커뮤니티 또는 관리자 기능 중 어느 것도 관찰 전에 웨지로 고정하지 않는다. 사용자가 제시한 다음 세 방향은 별도 검증 후보로 둔다.

| 후보 방향 | 검증할 전환 이유 | 선행 위험 |
|---|---|---|
| 부상 이력 기반 회피·안전 필터 | 기존 로거가 금기·불안 때문에 쓰이지 않는지 | 의료 목적 오인, 상해·금기 정확성, 임상·법률 검토 |
| 헬스장·PT샵 B2B2C | 트레이너의 배정·수행 확인 업무에 계약 예산이 있는지 | 트레이너 운영 흐름, 다중 회원 개인정보, 대시보드 범위 |
| 회복 데이터 기반 적응형 코칭 | 수면·심박·회복에 따른 당일 조정에 지불하는지 | Health Connect 권한, 알고리즘 안전성, AI 원가, 기존 SensAI 대안 |

“가장 유망”이라는 순위는 사용자 인터뷰, 실제 대안과 지불 행동이 없으므로 이 문서에서 확정하지 않는다.

## Constraints

### Repository and process

- **확인됨:** 저장소 최상위 실행 규칙은 루트의 `CLAUDE.md`다.
- **확인됨:** 신규 작업은 `develop`에서 새 `feat/*`, `fix/*`, `chore/*`, `docs/*` 브랜치를 만든 뒤 수행한다.
- **확인됨:** 설계·계획·명세·검토·보고 문서는 플랫폼이 루트 경로를 강제하지 않는 한 `docs/` 아래에 둔다.
- **확인됨:** `wiki/`는 기존 근거와 GitHub Wiki 게시 작업 공간이며, 새 계획 문서의 기본 위치가 아니다.
- **확인됨:** 기능 변경은 실패하는 테스트를 먼저 작성한 후 최소 구현을 작성하고, 실제 빌드 설정에서 확인한 명령으로 검증한다.
- **차단:** 현재 구현과 빌드 설정이 없으므로 애플리케이션 빌드·테스트 통과를 주장할 수 없다.

### Product and organization

- **미확인:** 백엔드 1명과 모바일 1명, MVP 14주라는 Wiki 제약이 실제로 승인되었는지 확인되지 않았다.
- **미확인:** Android 14 이상 실기기, 외부 AI 계정, 개발 인프라와 운영 담당자를 사용할 수 있는지 확인되지 않았다.
- **외부 근거:** Google Play 공개 배포에서 Health Connect 데이터 타입을 사용하려면 Play Console의 Health apps declaration, 데이터별 필요성 설명과 일치하는 공개 개인정보처리방침이 필요하다. 사용하지 않는 타입은 요청하면 안 된다.
- **외부 근거:** 현재 Google Play Console 요구사항은 건강 앱 등 지정 범주의 개발자 계정을 Organization으로 등록하는 요건을 2026-09-30 시행으로 표시한다. 제보된 “기존 건강 앱은 2026-01-28까지 이전” 주장은 Google의 현재 공식 자료에서 확인되지 않았다.
- **외부 근거:** Google의 Health apps declaration 안내는 Play의 private apps를 신고 대상에서 제외한다. 따라서 공개 Play와 관리형 비공개 배포는 같은 규제·게시 경로로 가정하지 않는다.
- **외부 근거:** 대한민국 개인정보 보호법은 건강정보를 민감정보로 두고 별도 동의 또는 법령상 근거와 안전조치를 요구한다. 국외 이전은 별도 동의만이 아니라 계약 이행상 필요한 처리위탁·보관 등 법이 정한 여러 근거 중 하나를 충족해야 한다.
- **미확인:** Claude/OpenAI 요청이 실제로 어느 국가·리전에 처리·보관되는지, 어떤 계약과 데이터 보존 설정을 적용할지는 공급자·엔드포인트·계약을 정하기 전에는 알 수 없다.
- **차단:** 민감정보를 수집·관찰·추론·저장하는 모든 단계는 데이터 최소화, 처리 근거, 동의, 접근 권한, 보관·폐기, 국외 이전과 사고 대응 방식을 담당 부서가 먼저 승인해야 한다.
- **차단:** 부상·재활·회복 기반 권고는 면책 문구만으로 비의료 서비스가 된다고 가정하지 않는다. 사용 목적·표현·알고리즘·대상에 대해 개인정보·법무와 필요 시 의료기기 규제 담당자의 분류 검토를 먼저 받는다.
- **차단:** 커뮤니티 기능은 심사·신고·이의제기를 맡을 운영 책임자와 서비스 수준이 정해져야 한다.

## Premises — Confirmed in Office Hours

아래 항목은 대화에서 승인한 전제다. 프로그램 또는 예산 승인 기록은 아니며, 이 문서가 `APPROVED`로 바뀌기 전에는 제안 상태다.

1. 현재 아무것도 하지 않을 때의 비용은 측정되지 않았다. Wiki의 18주 계획은 구현 승인 범위가 아니라 가설 목록이다.
2. 첫 목표는 실제 후보 사용자와 후원자를 찾고, 하나의 반복 문제·현재 대안·손실을 확인하는 것이다.
3. Wiki는 범위와 수치가 충돌하므로 단일 진실 공급원으로 사용하기 전에 정합성을 복구한다.
4. Health Connect의 기술적 구현 가능성은 제품 수요의 증거가 아니다.

## Approaches Considered

### Approach A: 1주 수요 검증 스프린트

제품 코드를 작성하지 않고 후보 사용자와 후원자를 만나 실제 업무와 손실만 확인한다. 가장 적은 비용으로 현재 증거 공백을 채우지만 단계별 프로그램 구조와 기술 검증은 다루지 않는다.

### Approach B: 2~3주 컨시어지 파일럿

짧은 발견 작업 후 폼, 스프레드시트, 기존 앱과 수작업 리포트로 한 결과를 대신 제공한다. 실제 반복 사용을 빨리 볼 수 있지만 수작업 서비스가 제품 유지율을 과대평가할 수 있고 오프라인·연동·보안 구조를 검증하지 못한다.

### Approach C: 증거 게이트형 단계별 제품 프로그램 — 선택됨

최소 문서 감사, 수요·시장, 무코드 가치·리텐션·수익성, 규제·구현 준비, 단일 수직 슬라이스, 제한 파일럿과 확장을 각각 독립 게이트로 운영한다. 장기 기능은 가설 백로그로만 보존하고 검증되지 않은 전체 범위를 한 번에 구현하지 않는다.

## Recommended Approach

### Operating model

선택된 C는 “18주 전체 기능을 즉시 착수한다”는 선택이 아니다. 각 투자를 바로 앞 단계의 증거로 승인하고, 증거가 없는 장기 기능은 폐기 가능한 가설로 남긴다는 선택이다.

#### Gate state transitions

- `GO`: 해당 게이트의 필수 증거와 필수 검토가 모두 충족되어 다음 게이트의 준비 작업만 허용한다.
- `LOOP`: 결정문에 지정한 동일 게이트 또는 이전 게이트로 돌아간다. 결정문에 없는 기능 추가와 다음 게이트 구현은 금지한다.
- `STOP`: 현재 웨지와 프로그램 지출을 닫는다. 재개하려면 새로운 증거, 재개 승인자와 새 결정 ID가 필요하다.
- 부분 증거는 `GO`가 아니다. 조건부 승인은 허용하지 않고, 범위를 줄여 모든 조건을 충족하거나 `LOOP`한다.

각 게이트는 시작 전에 진입 기록을 가져야 한다. 아래 **공통 필드**는 모든 게이트에 필수다.

- 결정 ID, 범위, 시작일과 종료 판단일
- 책임자, 증거 소유자, 필수 검토자, 승인자와 거부권자
- 허용 자원, 최대 반복 횟수와 초과 시 종료·상향 경로
- 원자료 보관 위치, Git에 남길 비식별 요약과 삭제일
- 증거 확인일, 적용 범위, 재검증일 또는 무효화 트리거

G1·G2·G4·G5처럼 실험·관찰을 판정하는 게이트에는 다음 **측정 필드**도 필수다.

- 기준선 산식, 목표, 관찰 단위, 대상 선정·제외 조건
- 표본 또는 기간을 선택한 근거
- 누락 데이터, 중도 이탈, 예외와 실패를 처리하는 규칙

구조적으로 적용되지 않는 필드는 비워 두지 않고 `N/A` 사유, 대체 통제와 해당 분야 검토자의 전자 승인을 기록한다. 제품 책임자는 안전·개인정보·법률·규제·재무 필드를 단독으로 `N/A` 처리할 수 없다.

#### Common measurement definitions

| 용어 | 운영 정의 |
|---|---|
| 동일 업무 | 같은 시작 조건, 목적과 완료 결과를 가진 반복 행위. 세부 단계 차이는 기록한다. |
| 직접 관찰 | 연구자가 데모하거나 조작을 지시하지 않고 실제 또는 승인된 재현 환경에서 행동·시간·오류를 기록함 |
| 안내 없음 | 사전에 등록한 도움 기준을 넘는 설명·수정·대리 조작이 없음 |
| 반복 사용 | 측정 계획에 정의한 서로 다른 업무 주기에서 같은 해결책을 다시 선택함 |
| 대안 전환 | 기존 도구를 병행한 것이 아니라 정의된 업무 결과에 선택된 해결책을 사용함 |
| 개선 | 사전 등록한 산식과 목표를 충족함. 인터뷰 만족도만으로 대체하지 않음 |
| 고위험 결함 | 승인된 심각도 표에서 안전·민감정보·데이터 손실·권한 우회·롤백 불능에 해당함 |
| 운영 한계 | 지원 시간, 오류율, 비용, 처리량 등 후원자가 사전에 허용한 최대값 |

| G-1 | 위임 범위, 임시 책임자, 조달·검토 리드타임 확인 | 수요·경제성 통과 주장, 제품 코드 |
| G0A–G1 | 문서 감사, 인터뷰, 관찰, 경쟁 제품 확인 | 제품 코드, 프로덕션 데이터 수집, 기능 일정 확정 |
| G2A | 클릭 시안, 합성 데이터 사용성 시험 | 실제 효과·리텐션 통과 주장, 신규 프로덕션 백엔드 |
| G2B | 승인된 기존 도구와 수작업 서비스 | Health Connect·LLM·회원 시스템을 선행 구현 |
| G0B–G3 | 영향 문서 정리, 규제·보안 검토, 제한된 기술 POC | 웨지 밖 모듈 구축, 파일럿 배포 |

| G5 | 승인된 제한 코호트 운영 | 목표 확인 전 전체 조직·외부 공개 확대 |
| G6 | 별도 미니 게이트를 통과한 기능 | 이전 Wiki 일정만으로 기능 착수 |

### G-1 — 위임·책임자 부트스트랩

**목적:** 수요를 아직 검증하지 못한 시점의 순환 문제를 끊는다. 프로그램을 의뢰할 권한이 있는 **위임 책임자**가 한시적으로 사람·시간·발견 비용을 승인하고, **임시 후원자**가 G0A와 G1만 책임진다. 이 임시 지정은 G1이 요구하는 경제적 후원자나 수요 증거로 계산하지 않는다.

**필수 산출물:** 위임 근거와 만료일, G0A/G1의 자원 한도, 임시 후원자·제품/증거 책임자·개인정보 검토자, 모집 가능한 사용자 대표, 필요한 재무·법무·규제·안전·기술 검토의 조달 방식과 예상 리드타임을 기록한다.

**통과 조건:** 위임 책임자가 G0A/G1에 한정된 `GO/STOP` 권한과 비용 한도를 서명하고, 필수 역할을 이름으로 배정한다. 임시 후원자의 권한은 G1 결정과 함께 만료하며, G1에서는 관찰된 문제의 비용과 실제 예산 경로에 책임지는 경제적 후원자를 별도로 검증한다.

**중단 조건:** 위임 책임자, 한시적 자원 또는 발견 단계의 개인정보 검토자를 배정할 수 없으면 프로그램을 시작하지 않는다.

### G0 — 최소 감사와 영향 범위 정합성

#### G0A — 발견 전 최소 권위·안전 감사

**목적:** 문서 고고학이 사용자 발견을 막지 않게 하면서, 어떤 문서를 믿을지와 발견 단계의 안전 경계를 정한다.

**고정 감사 말뭉치:** 이 문서의 Repository sources에 열거한 Wiki 파일 12개와 루트 `CLAUDE.md`의 총 13개 파일이다. 상세설계 참조 충돌을 판정하기 위해 상세설계 v1과 v2를 모두 포함한다. 현재 집계 해시는 Evidence Register의 `REP-007`에 고정한다. 말뭉치를 추가하거나 파일 내용이 바뀌면 감사 버전, 해시와 결정 ID를 새로 만든다.

**현재 확인된 충돌:**

| 주제 | 문서 A | 문서 B 또는 실제 집계 | 처리 요구 |
|---|---|---|---|
| 요구사항 수 | Wiki README: 136건 | 요구사항 v2 명시 항목: FR 152건 + NFR 55건 = 207건 | 정의와 집계 규칙을 확정하고 자동 재계산 가능하게 함 |
| ERD 수 | ERD v2 변경란: 42테이블 | 같은 문서 엔티티 목록: 43개 | 누락 또는 메타데이터 오류 확정 |
| 테스트 케이스 수 | README·테스트보고서: 235건 | 테스트케이스 v2의 서로 다른 ID: 237개 | 중복·누락 여부와 공식 총계 확정 |
| 관리자 범위 | 요구사항 v2: 관리자 백엔드는 MVP | 계획서 v5·변경요청서 v2: A2~A4, MVP 이후 | 하나의 승인 범위로 통일 |
| 서버 모듈 수 | NFR-301: 8개 | 아키텍처 v2: 기능 모듈 10개 + `shared` | 모듈 정의와 개수 통일 |
| 상세설계 참조 | 아키텍처 v2: 상세설계 v1 참조 | 상세설계 v2 파일 존재 | 참조 버전 확정 |
| 구현 진행 상태 | 작업로그: Flutter 스캐폴딩·Docker 진행 | 현재 저장소: 빌드·실행 설정 없음 | 실제 소스 저장소 또는 산출물 경로 확인 |

**G0A 필수 산출물:**

- 고정 말뭉치, 버전별 문서 목록과 임시 문서 소유자
- 사용자 발견에 영향을 주는 범위, 안전, 데이터, 배포 주장의 상태
- 각 알려진 충돌의 소유자와 이후 처리 게이트
- 문장별 `확인됨 / 외부 근거 / 제안됨 / 미확인 / 차단` 분류 원칙
- Wiki와 `docs/` 사이의 게시·동기화 규칙

**G0A 통과 조건:** 발견에 사용할 가설 목록, 안전 경계, 문서 권위와 알려진 충돌 목록을 식별할 수 있다. 모든 수치 충돌을 해결할 필요는 없다.

#### G0B — 선택된 웨지 영향 문서 정합성

G2B에서 웨지가 통과한 뒤 해당 웨지가 참조하는 요구사항, API, 데이터, 테스트, 일정과 배포 문서만 상세 정리한다. 위 표의 충돌 중 웨지와 무관한 항목은 백로그로 남기고 구현 차단 사유로 사용하지 않는다.

**G0B 통과 조건:** 선택된 웨지의 요구사항·데이터·테스트 ID가 서로 추적되고, 범위 충돌이 없으며, 모든 완료 주장을 재현할 수 있다.

**중단 조건:** 문서 범위와 승인자를 결정할 소유자가 없다면 프로그램을 진행하지 않는다.

### G1 — 실제 문제·시장·후원자 증거

**목적:** 기능 설명 없이 현재 업무를 관찰하고, 문제가 실제인지, 무료·유료 대안에서 전환할 이유와 결정권자가 있는지 확인한다.

**조사 규칙:**

- FitPulse 데모나 제안 기능을 먼저 보여주지 않는다.
- 참여자가 평소 쓰는 도구와 순서로 업무를 수행하게 한다.
- 발언보다 행동, 실제 기록, 시간과 실패 사례를 우선한다.
- 건강정보 원문과 식별 가능한 직접 인용은 Git에 저장하지 않는다. 승인된 연구 저장소에는 동의 범위만 보관하고 Git에는 편집된 요약과 불투명한 증거 ID만 남긴다.
- Strong, Hevy와 참여자가 실제 사용하는 대안의 당시 무료·유료 제한을 직접 확인한다.
- 부상 안전, B2B2C, 회복 코칭 후보를 같은 질문으로 유도하지 않고 별도 문제 가설로 시험한다.

**제안된 최소 통과 기준:**

- 명시된 주 사용자 1명 이상과 경제적 내부 후원자 1명 이상
- 최소 2명의 참여자에게서 동일한 업무를 총 3회 이상 직접 관찰
- 현재 업무의 단계, 빈도, 기준선, 실패 결과와 대체 도구 기록
- 기존 대안에서 바꿀 구체적 이유, 문제로 인한 현재 지출·손실의 소유자, 경제적 구매자와 실제 예산·조달 경로
- 후원자가 측정 지표, 목표, 파일럿 자원과 `GO/STOP` 권한을 서면으로 명시
- 시작 전 서명된 측정 계획에 대상·산식·목표·누락·이탈·판정 규칙을 기록

이 숫자는 시장 사실이 아니라 허술한 단일 인터뷰 승인을 막기 위한 프로그램 규칙이다. 통과해도 해당 참여자와 업무에 대한 국소 증거일 뿐, 조직 전체나 외부 시장 수요로 일반화하지 않는다. 더 엄격한 내부 연구 기준이 있으면 그 기준으로 대체한다.

**중단 조건:** 반복 문제, 전환 이유, 현재 대안 또는 후원자를 확인하지 못하면 제품 개발을 중단하거나 다른 문제로 `LOOP`한다.

### G2 — 무코드 사용성·가치·리텐션·수익성 검증

#### G2A — 사용성 검증

클릭 가능한 흐름과 합성 데이터로 이해도, 탐색과 오류 복구를 확인한다. G2A는 사용성 문제만 찾으며 실제 결과 개선, 리텐션 또는 지불 의사를 통과시킬 수 없다.

시험 전에 G1의 핵심 업무별 시작·완료 상태, 무안내 성공 기준, 허용 시간·도움·복구 기준, 대표 사용자 선정 근거와 최대 반복 횟수를 등록한다. 사용성 심각도는 다음처럼 판정한다.

- `U1`: 안전·권리·민감정보·데이터 손실을 유발할 수 있음
- `U2`: 핵심 업무를 완료하거나 정해진 복구 경로로 회복할 수 없음
- `U3`: 완료는 가능하지만 심각한 지연·오류·과도한 도움을 유발함
- `U4`: 결과 완료를 막지 않는 경미한 문제

**통과 조건:** 사전 등록한 각 핵심 업무를 해당 사용자 유형의 독립된 대표가 안내 없이 한 번 이상 완료하거나 허용된 복구 기준 안에서 회복하고, 미해결 `U1`·`U2`가 없으며, 사용자 대표와 검증 책임자가 결과를 공동 승인한다. 표본은 효과 추정이 아니라 핵심 흐름 결함 탐색에만 적용하며 선정 근거를 남긴다.

**중단 조건:** `U1`·`U2`가 남거나 핵심 업무가 등록 기준을 충족하지 못하면 시안을 수정해 `LOOP`한다. 최대 반복 횟수 안에 해결하지 못하면 해당 흐름을 폐기하거나 G1의 문제·사용자 선택으로 돌아간다.

#### G2B — 수작업 가치·반복 사용 검증

기존 도구와 승인된 수작업 처리로 한 사용자 결과를 실제 제공한다. 사용자 계정, 신규 백엔드, Health Connect와 LLM 통합은 기본적으로 포함하지 않는다.

**통과 조건:**

- G1의 기준선과 같은 방식으로 결과를 다시 측정
- 측정 계획에 정의한 서로 다른 업무 주기에서 사용자가 안내 없이 다시 선택한 증거
- 후원자가 사전에 정한 목표 달성 여부와 다음 투자 결정을 기록
- 개인정보·보안 검토가 다음 단계의 데이터 범위를 승인
- 제안한 결과·범위·기간·가격 또는 내부 비용분담 조건에 연결된 실제 승인·결제·발주·계약 행동 중 하나. 단순한 “예산이 있다”는 응답은 통과 증거가 아님
- 유료·무료 사용량 가정별 수익과 변동비를 계산한 첫 단위 경제 모델

**중단 조건:** 결과가 개선되지 않거나 반복 사용이 없으면 기능을 더 추가하지 않고 문제·사용자·제공 방식을 다시 선택한다.

### G3 — 규제·안전·경제성·구현 준비

**목적:** 선택된 웨지 하나를 테스트 우선으로 구현할 수 있는 상태를 만든다.

**필수 결정:**

- 선택된 웨지에 실제로 필요한 소스 저장소와 소유권. 모바일·서버·관리자는 필요 없는 경우 `N/A`로 기록
- 소스가 다른 저장소에 있는지, 채택할지, 새로 만들지와 각 경로의 비용·조달 시간
- 실제 빌드 파일, 언어·프레임워크·의존성 버전
- 한 수직 슬라이스의 입력, 상태 변화, 출력과 실패 모드
- Given/When/Then 형식의 인수 조건과 첫 실패 테스트 목록
- 개발·검증 환경, 실기기, 외부 계정과 비밀 관리 방식
- 공개 Play, 관리형 비공개 또는 다른 실제 배포 채널, 승인자, 롤백과 지원 경로
- 관측 지표와 개인정보 최소 수집 범위
- 위협 모델, 인증 강도, 전송·저장 보호, 백업·복구, 정보주체 요청과 사고 대응 기준
- 부상·건강 권고의 금기, 이상 사례 보고, 의료·웰니스 경계, 대상 연령과 접근성 기준

**아키텍처 정책:** Flutter 3.47, Spring Boot 4.1, Java 21, MySQL, Redis, MinIO와 모듈러 모놀리스는 Wiki의 후보 결정이다. 실제 저장소, 호환성, 운영 제약을 읽어 검증한 뒤 채택·수정한다. 선택된 웨지에 필요하지 않은 모듈과 외부 서비스는 만들지 않는다.

**Health Connect 조건:** 선택된 웨지가 Health Connect에 의존할 때만 2026-08-14에 확인한 공식 문서와 실제 SDK 버전을 다시 대조하고, 권한·변경 토큰·upsert·삭제·자사 데이터 제외·토큰 만료·백그라운드를 실제 기기에서 POC한다. 공개 Play라면 Health apps declaration, 최소 데이터 타입과 일치하는 개인정보처리방침, 당시 계정 유형 요건을 제출 계획에 포함한다. 이 기술·스토어 검증은 수요 게이트를 대신하지 않는다.

**대한민국 데이터 조건:** 건강정보 처리 근거와 별도 동의, 안전조치, 공급자별 실제 처리 리전, 국외 이전의 법적 근거·고지·계약을 개인정보·법무 담당자가 확인한다. `AI_PROCESSING` 체크박스 하나로 모든 의무를 충족한다고 가정하지 않는다.

**Economics gate:** Wiki의 “사용자당 10회/일”은 상한이지 실제 사용량 예측이 아니다. 다음 식을 실제 모델·토큰·재시도·폴백·스토어 조건으로 계산한다.

`월 공헌이익 = 결제액 - 스토어/결제 수수료 - LLM 입력·출력·재시도·폴백 비용 - 저장·전송·관측 비용 - 변동 지원 비용 - 환불·세금 조정`

평균, 상위 사용량과 허용 상한의 세 시나리오에서 계산하고, 무료 사용자의 월 예산 상한과 하드 제한을 정한다. 현재 모델명, 토큰 사용량과 실제 호출 빈도가 없으므로 “월 원가가 구독료를 넘는다” 또는 그 반대를 확정하지 않는다. 일 `$10` 알림은 비용 관측일 뿐 사업 모델 통과 기준이 아니다.

G2B를 시작하기 전에 재무/예산 담당자와 후원자는 결과를 보기 전 다음 임계값을 서명한다.

| 경제성 차원 | 사전 등록할 기준 | 판정 시점 |
|---|---|---|
| 변동 공헌이익 | 가격·수수료·환불·세금·평균/P90/상한 사용량별 최소 금액과 최소 비율 | G2B 추정, G3 구현 예산 승인, G5 실측 |
| 획득비용·회수기간 | 외부 판매 채널별 최대 CAC와 최대 회수기간 | G3 채널 계획, G5 실측 |
| 리텐션·LTV | 보수적 유지기간과 이탈 규칙, `LTV = 유지기간 내 누적 공헌이익`의 최소 CAC 배수 | G2B 하한 추정, G5 코호트 실측 |
| 고정비·런웨이 | 개발·규제·보안·지원·스토어 준비비의 상한과 다음 증거까지 허용할 현금·인력 기간 | G3 |
| 내부 배포 가치 | 현재 손실·지출 기준선, 보수적 절감액, 총비용, 최대 회수기간 | G1 기준선, G2B 약정, G3 예산, G5 실측 |

외부 판매가 아니어서 CAC·가격·LTV가 구조적으로 적용되지 않으면 재무/예산 담당자와 후원자가 `N/A`를 공동 서명하고 내부 배포 가치 기준으로 대체한다. 결과를 본 뒤 임계값을 낮출 수 없다. 모든 적용 기준을 충족하지 못하면 범위·가격·채널을 바꿔 `LOOP`하거나 `STOP`한다.

**통과 조건:** 해결되지 않은 차단 결정이 없고, 인수 조건·첫 실패 테스트·실제 환경 접근·필요 의존성·배포·롤백·데이터·안전 책임자가 승인되어 있다. 또한 모든 적용 가능한 경제성 임계값이 보수적 시나리오에서 충족되고 고정비·런웨이가 승인된 한도 안에 있어야 한다. G5의 실측 리텐션과 CAC가 나오기 전에는 외부 시장 확대를 승인하지 않는다.

### G4 — 통제된 단일 수직 슬라이스

**목적:** 프로덕션 확대 전에 승인된 테스트 환경과 사전 등록된 참여자·시나리오에서 한 사용자 결과를 끝에서 끝까지 검증한다. G4는 지속 운영 파일럿이 아니다.

**실행 규칙:**

1. 실패하는 테스트로 사용자 결과와 실패 모드를 먼저 고정한다.
2. 해당 테스트를 통과시키는 최소 구현만 작성한다.
3. 실제 빌드 설정에서 확인한 정적 분석·단위·통합·기기 또는 브라우저 테스트를 실행한다.
4. 배포 전 롤백과 관측 경로를 검증한다.
5. 테스트 결과와 남은 위험을 `docs/verification/`에 기록한다.

**통과 조건:** 선택된 슬라이스의 인수 테스트가 통과하고, 승인된 통제 관찰에서 G2와 같은 결과를 재현하며, 사전 합의한 심각도 표의 미해결 고위험 결함이 없다.

**중단 조건:** 테스트를 우회해야만 시연할 수 있거나 사용자 결과가 재현되지 않으면 기능 범위를 확대하지 않는다.

### G5 — 제한 운영 파일럿

**목적:** 제한된 실제 운영 환경에서 시간에 따른 반복 사용, 중도 이탈, 운영 부담과 결과 지속성을 확인한다.

파일럿 인원과 기간은 G1/G2 기준선, 기대 효과와 조직 제약을 바탕으로 후원자가 승인한다. 이 문서에서는 근거 없는 사용자 수나 유지율 목표를 고정하지 않는다. 측정 계획은 활성화, D7/D30 또는 업무 주기별 리텐션, 자발적 중단, 연락 두절과 누락 데이터를 구분한다.

**필수 조건:** 참여 동의·철회, 데이터 최소화, 접근 통제, 지원 담당자, 장애·이상 사례 연락 경로, 기능 중단 스위치, 롤백, 시작 전 기준선, 종료 판단일과 원자료 삭제일.

**통과 조건:** 사전에 정한 제품 결과, 리텐션·경제성 임계값과 운영 한계를 충족하고 후원자가 확대 비용과 책임자를 승인한다. 미해결 `U1`·`U2` 또는 고위험 안전·개인정보·보안·규제 사건이 없고, 모든 사건에 책임자·근본 원인·시정·재검증 결과가 있는 서명된 종료 검토를 남긴다. 정보 내보내기와 삭제, 접근 회수, 롤백·킬스위치와 사고 연락망을 운영 환경에서 실행해 통과해야 한다.

### G6 — 증거 기반 기능 확장

아래 목록은 비권위적인 가설 백로그다. 확장 기능은 트리거가 확인될 때만 별도 미니 게이트를 연다.

| 기능군 | 착수 증거 | 추가 검증 |

| 오프라인 동기화 | 실제 장소에서 연결 손실이 기록 실패를 만든 관찰 | 앱 종료·재시도·충돌·중복·복구 실기기 테스트 |
| Health Connect | 수기 건강 데이터 업무의 측정된 비용과 자동화 동의 | 권한 거부·변경 토큰·삭제·중복·백그라운드 제약 |
| AI 루틴 | 루틴 구성의 반복 손실과 수작업·템플릿 기준선 | 안전 규칙, 미매핑, 비용, 지연, 공급자 장애, 비식별화 |
| 분석 | 사용자가 특정 의사결정에 실제 지표를 사용 | 계산 정확성, 지연, 빈 상태와 설명 가능성 |
| 커뮤니티 | 사용자 간 공유 행동과 발견 문제 | 심사 용량, 신고·제재·이의제기, 위험 콘텐츠 대응 |
| 관리자 도구 | 반복 운영 건수와 수기 처리 위험 | 최소 권한, 2FA, 감사, 대량 작업, 롤백, 운영 인력 |

Wiki의 W1~W14와 A1~A4는 이 게이트를 통과한 기능에 한해 다시 산정한다. 기존 18주 숫자는 일정 기준선으로 승계하지 않는다.

각 미니 게이트는 다음을 반드시 가진다.

- 수요 증거와 해당 증거의 적용 범위
- 책임자, 필수 검토자, 승인자와 안전·개인정보 거부권자
- 측정 계획, 시간·자원 한도와 최대 반복 횟수
- 기능별 인수 테스트, 실패·롤백·중단 조건
- 기존 데이터·권한·비용·운영 부담에 누적되는 영향
- 증거 만료 또는 정책·API·사용자군 변경 시 재검증 조건

## Program Artifact and Source-of-Truth Design

새 산출물은 다음 위치를 사용한다. 이 문서는 디렉터리 구조만 정의하며 Office Hours 단계에서 추가 문서나 구현 스캐폴딩을 만들지 않는다.

| 경로 | 용도 | 권위 |
|---|---|---|
| `CLAUDE.md` | 저장소 전체 실행 규칙 | 최상위 통제 문서 |
| `docs/design/` | 승인 전·후 제품 및 기술 설계 | 승인된 설계가 프로그램 방향을 통제 |
| `docs/discovery/` | 관찰 계획, 편집된 비식별 요약, 원자료를 가리키는 불투명한 증거 ID | 수요 판단의 검토본. 식별 가능한 원자료는 금지 |
| `docs/decisions/` | 게이트 결정과 ADR | 결정 일시 이후의 공식 선택 |
| `docs/plans/` | 승인된 단계의 실행 계획 | 해당 게이트 범위에서만 유효 |
| `docs/reference/wiki-audit/` | Wiki 버전·수치·링크 정합성 결과 | G0 재현 근거 |
| `docs/verification/` | 테스트 실행, 파일럿 지표, 배포 검증 | 완료 주장의 근거 |
| `wiki/` | 기존 근거와 GitHub Wiki 게시본 | 게시용 사본·역사 자료 |

문서 변경 흐름은 `docs`에서 검토·승인한 후 필요한 내용을 `wiki` 게시본에 반영하는 방향으로 통일한다. `CLAUDE.md`는 항상 실행 규칙의 최상위다. 제품 방향에서는 **적용 범위와 발효 시점이 같은 가장 최신의 승인된 `docs/decisions/`가 기존 설계를 우선**하고, 그 결정이 설계에 반영될 때까지 차이를 G0 색인과 설계 상태에 표시한다. 최신 결정이 없는 범위에서는 승인된 `docs/design/`이 우선하며, `wiki/`는 어느 경우에도 승인 결정을 덮지 않는다.

### Naming and status convention

- 증거 요약: `docs/discovery/EVD-YYYY-NNN-<slug>.md`
- 게이트 결정: `docs/decisions/GATE-<gate>-YYYYMMDD-NNN.md`
- 측정 계획: `docs/plans/MEASURE-<gate>-YYYYMMDD-NNN.md`
- 검증 결과: `docs/verification/VERIFY-<decision-id>-YYYYMMDD.md`
- 상태: `DRAFT → IN_REVIEW → APPROVED → SUPERSEDED` 또는 `REJECTED`
- 승인 문서는 승인자, 승인 시각, 적용 범위, 원자료 ID, 다음 재검증일 또는 무효화 트리거를 front matter에 기록한다.

식별 가능한 녹취, 원문 인용, 연락처, 동의서와 신원 매핑 키는 Git 밖의 조직 승인 연구 저장소에 둔다. Git에는 철회·삭제가 가능한 원자료 위치를 직접 노출하지 않고 증거 ID만 남긴다.

### Canonical gate-decision record

모든 게이트 결정문은 최소한 다음 항목을 포함한다.

1. 결정 ID, 게이트, 상태와 버전
2. 책임자·증거 소유자·필수 검토자·승인자·거부권자
3. 진입 범위, 시간·자원 한도, 최대 반복 횟수
4. 적용되는 측정 계획 ID와 사전 등록된 판정 규칙, 또는 서명된 `N/A` 사유와 대체 통제
5. 사용한 증거 ID, 확인일, 적용 범위와 만료 조건
6. 충족·미충족 조건과 `GO/LOOP/STOP` 근거
7. 허용되는 다음 작업과 금지되는 작업
8. `LOOP` 목적지 또는 `STOP` 재개 조건
9. 원자료·파생자료·백업의 보존·삭제일, 삭제 증명과 민감정보 검토 결과
10. 결정자 서명 또는 조직에서 인정하는 전자 승인 기록

## Governance

역할은 지금 이름이 아니라 책임으로만 정의한다. 각 게이트 진입 기록에서 실제 담당자를 배정하지 못하면 시작할 수 없다.

| 역할 | 책임 | 단독 승인 제한 |
|---|---|---|
| 위임 책임자 | G-1의 한시적 발견 위임, 비용 한도와 임시 책임자 지정 | G1 수요·지불 증거를 대신 만들지 않음 |
| 경제적 내부 후원자 | 문제 비용, 목표, 예산, 파일럿과 `GO/STOP` | 기술·개인정보·재무 예외를 단독 승인하지 않음 |
| 제품 책임자 | 문제·웨지·범위와 증거 정합성 | 자신의 가설·시안을 스스로 통과시키지 않음 |
| 증거 소유자 | 원자료 연결, 동의·수집 절차, 증거 계보와 만료 관리 | 자신이 수집한 증거의 유일한 검증자가 되지 않음 |
| 사용자 대표 | 실제 업무·언어·사용성 결과가 사용자 현실을 반영하는지 검토 | 제품팀의 대리 의견으로 대체하지 않음 |
| 검증 책임자 | 측정 계획, 테스트 독립 실행, 결함 심각도와 결과 재현 | 자신이 구현한 변경의 유일한 승인자가 되지 않음 |
| 기술 책임자 | 구조, 테스트, 배포, 운영 가능성 | 수요 게이트를 기술 POC로 대체하지 않음 |
| 재무/예산 담당자 | 가격·비용·CAC·회수기간·런웨이 산식과 임계값 | 제품 책임자가 결과를 본 뒤 임계값을 바꾸게 하지 않음 |
| 개인정보·보안 책임자 | 처리 근거, 데이터 범위, 접근, 보관·폐기, 사고 대응 | 제품 성과를 대신 판정하지 않음 |
| 법무 책임자 | 동의·계약·국외 이전·책임·표현의 법적 적용성 | 제품 면책 문구만으로 위험을 승인하지 않음 |
| 규제 책임자 | 사용 목적, 배포 국가·채널과 의료기기·스토어 분류 | 미확인 분류를 `N/A`로 처리하지 않음 |
| 안전/임상 책임자 | 위해 분석, 금기, 이상 사례와 안전성 검증 기준 | 임상 자격이 필요한 판단을 제품팀에 위임하지 않음 |
| 운영 책임자 | 지원, 신고·제재, 장애·사고 대응과 종료 처리 | 책임자 미배정 상태로 파일럿·커뮤니티를 열지 않음 |

### Role independence and minimum staffing

아래는 기본 다인 조직 모델이다. FitPulse V0~V2에는 ADR-20260814-001을 적용해 개인사업자 본인 `R-OWNER` 한 명이 역할 기능을 순서대로 수행한다. 해당 범위의 결과는 `OWNER_SELF_REVIEW`이며 독립 검증 완료를 주장하지 않는다. G3 이후와 법령·계약·스토어가 별도 자격이나 검토를 요구하는 항목은 이 예외로 면제되지 않는다.

- 제품 책임자와 G2A 최종 사용성 승인자는 분리한다. 사용자 대표와 검증 책임자가 공동 승인하며 제품 책임자는 증거를 제출한다.
- 증거 소유자와 검증 책임자는 같은 증거 묶음의 유일한 수집자·검증자를 겸할 수 없다. G4 구현자도 자신이 만든 변경의 유일한 시험 실행자나 최종 승인자가 될 수 없다.
- 사용자 대표는 해당 업무를 수행하거나 직접 대표할 위임을 받아야 하며 제품 가설의 작성자로 대체하지 않는다.
- 법무·규제·안전/임상 책임은 자격과 서면 위임이 확인된 내부 담당자 또는 외부 전문인에게 맡긴다. 한 사람이 여러 분야를 맡을 때는 분야별 역량·이해충돌·승인을 각각 기록하며, 해당 분야 거부권은 경제적 후원자가 무효화할 수 없다.
- 위임 책임자와 경제적 후원자는 G1에서 실제 비용·예산 책임이 확인된 뒤 같은 사람일 수 있다. 확인 전에는 임시 후원자 지정을 수요 증거로 계산하지 않는다.
- 최소 배정 기능은 G-1~G1에서 `위임/임시 후원`, `제품·증거`, `독립 사용자 대표`, `개인정보 검토` 4석이다. G2~G3에는 `검증`, `재무/예산`, `기술`을 추가하고, 적용 시 `법무`, `규제`, `안전/임상`을 추가한다. G4~G5에는 `운영`을 추가한다. 금지된 겸임을 제외하면 한 사람이 여러 석을 맡을 수 있으나 각 책임과 서명은 분리한다.
- 외부 전문 검토, 조직 계정, D-U-N-S, 실기기, 스토어 심사와 보안 검토의 예상 조달 리드타임은 G-1에서 처음 기록하고 G3 진입 전에 실제 담당자·발주 상태·완료 예정일로 갱신한다. 게이트 기간 안에 확보할 수 없으면 범위를 줄여 `LOOP`하거나 `STOP`한다.

### Gate decision matrix

| 게이트 | 책임자 | 필수 검토자 | 최종 승인자 | 거부권자 | 핵심 증거 | 미해결 시 경로 |
|---|---|---|---|---|---|---|
| G-1 | 위임 책임자 | 임시 후원자, 개인정보·보안 책임자 | 위임 책임자 | 개인정보·보안 책임자 | 위임·자원 한도·임시 역할·조달 리드타임 | 역할 확보 전 `STOP` |
| G0A | 문서 소유자 | 제품 책임자, 개인정보·보안 책임자 | 임시 후원자 | 개인정보·보안 책임자 | 고정 말뭉치, 권위·안전 감사 | 소유자 확보 기한까지 `LOOP`, 이후 `STOP` |
| G1 | 제품 책임자 | 증거 소유자, 사용자 대표, 재무/예산·개인정보 담당 | 위임 책임자와 검증된 경제적 후원자 | 개인정보·보안 책임자 | 관찰, 대안, 기준선, 전환 이유·현재 비용·예산 경로 | 다른 문제로 `LOOP` 또는 `STOP` |
| G2A | 제품 책임자 | 사용자 대표, 검증 책임자 | 사용자 대표와 검증 책임자 공동 | 개인정보·보안 책임자 | 사전 등록 업무, 무안내 성공·복구, U1~U4 결함표 | 시안 수정 `LOOP`; G2 전체 `GO` 불가 |
| G2B | 제품 책임자 | 사용자 대표, 검증·재무/예산·개인정보 담당 | 경제적 후원자 | 개인정보·보안 및 재무/예산 담당자 | 전후 결과, 반복 사용, 제안 조건에 대한 약정, 초기 경제성 | 웨지·제공 방식 `LOOP` 또는 `STOP` |
| G0B | 문서 소유자 | 제품·기술 책임자 | 제품 책임자 | 기술 책임자 | 웨지 추적성·정합성 | 영향 문서만 `LOOP` |
| G3 | 기술 책임자 | 제품, 검증, 개인정보·보안, 운영, 재무/예산 및 적용 시 법무·규제·안전/임상 | 경제적 후원자 | 기술·개인정보·재무 및 적용 시 법무·규제·안전/임상 | 분류·위해/위협 모델·시험 계획·경제성·저장소 준비 | 범위 축소 `LOOP` 또는 `STOP` |
| G4 | 기술 책임자 | 제품, 독립 검증, 개인정보·보안 및 적용 시 안전/임상 | 검증 책임자와 제품 책임자 공동 | 개인정보·보안 및 적용 시 안전/임상 | 구현된 통제·실행 테스트·통제 관찰·결함표 | 구현·테스트 `LOOP` |
| G5 | 운영 책임자 | 제품, 기술, 검증, 재무/예산, 개인정보·보안, 사용자 대표 및 적용 시 법무·규제·안전/임상 | 경제적 후원자 | 개인정보·보안·재무 및 적용 시 법무·규제·안전/임상 | 운영 지표·리텐션·비용·사건 종료 검토·삭제/내보내기 | 파일럿 조정 `LOOP` 또는 `STOP` |
| G6 | 기능별 책임자 | 영향받는 모든 책임자 | 경제적 내부 후원자 | 안전·개인정보 영향 책임자 | 미니 게이트 전체 | 기능별 `LOOP` 또는 폐기 |

거부권은 안전·민감정보·규제 또는 운영 불능을 막는 용도이며 제품 성과를 대신 승인하지 않는다. 의견 충돌은 결정문에 남기고 상위 조직 책임자에게 한 번만 상향한다. 상향 후에도 결론이 없으면 `STOP`이다.

## Data and Privacy Boundaries

- G1 참여자는 관찰 목적, 기록 항목, 사용 범위, 보관 기간, 철회 방법을 안내받는다. 동의하지 않으면 기록하지 않는다.
- 참여자 식별정보와 업무 관찰은 분리하고, 신원 매핑 키의 보관자와 접근자를 한정한다.
- 식별 가능한 직접 인용과 건강정보 원문은 Git에 저장하지 않는다. 재식별 가능성이 남은 소규모 집단·직무·사건 조합도 편집한다.
- 철회 요청이 오면 승인 연구 저장소의 원자료와 매핑 키를 삭제하고, Git의 비식별 요약이 재식별 가능한지 다시 평가한다.
- G2에서 민감정보가 필요하다는 주장은 먼저 비식별·합성 데이터로 검증한다.
- 민감정보를 관찰·수집·추론하기 전 데이터 항목별 목적, 처리 근거, 접근자, 저장 위치, 보관 기간, 삭제 트리거와 사고 대응을 승인한다.
- 외부 AI 전송은 웨지에 필수이고 별도 승인을 받은 경우에만 허용한다. 공급자 선택과 폴백은 실제 비용·가용성·데이터 조건으로 다시 결정한다.
- 파일럿 종료 시 보존할 지표와 삭제할 원자료를 미리 정한다.

데이터 수명주기는 게이트 진입 전에 개인정보·법무 담당자가 승인하고 다음 최소 항목을 갖는다.

| 자료 종류 | 활성 기간 통제 | 철회·종료 처리 | 검증 기록 |
|---|---|---|---|
| 동의·철회·접근 감사 최소 기록 | 원자료와 분리하고 법령·조직 정책상 필요한 항목만 제한 접근으로 보존 | 승인된 보존 의무가 끝나면 삭제. 철회 사실 자체의 최소 감사 기록은 법적 근거와 기간을 별도 명시 | 보존 근거·기간·접근자 승인 |
| 식별 가능한 원자료·녹음·신원 매핑 키 | 암호화, 역할별 접근, 목적별 저장소 분리 | 철회 또는 사전 종료일에 운영본과 복제본에서 삭제 | 항목·저장소·삭제 시각·실행자·검증자 서명 |
| 백업·스냅샷 | 백업 위치, 복구 권한, 순환 주기와 삭제 전파 최대기한을 사전 등록 | 즉시 선택 삭제가 불가능하면 접근을 봉쇄하고 다음 순환 삭제일을 기록하며 복구 시 삭제 요청을 재적용 | 백업 삭제 전파 또는 암호키 폐기 검증 |
| 파생 데이터셋·분석 결과 | 원천 증거 ID와 변환 계보, 재식별 위험, 사용 목적 기록 | 철회 범위가 재계산 가능한 경우 삭제·재생성하고, 불가능하면 근거와 영향 결정을 기록 | 재식별 검토와 재계산 결과 |
| 비식별 결정·검증 문서 | 식별자를 제거하고 사용한 증거 ID·적용 범위·만료를 기록 | 원천 증거가 철회·무효화되면 기록을 몰래 지우지 않고 `EVIDENCE_INVALIDATED`로 표시해 영향받은 결정을 재심사 | 영향 결정 목록과 재심사 서명 |
| 삭제 증명 | 삭제 요청별 운영본·백업·파생자료 범위를 추적 | 모든 적용 대상의 처리 후 닫음. 실패 항목은 사건으로 상향 | 개인정보 담당자와 독립 검증자 공동 서명 |

법적 보존 명령이 있으면 삭제를 조용히 생략하지 않는다. 법무 책임자가 근거·범위·만료일을 승인하고 자료를 사용 중지·접근 봉쇄하며, 해제 후 삭제와 증명을 재개한다.

이 문서는 법률 자문을 대신하지 않는다. 적용 의무는 조직의 개인정보·법무 담당자가 현재 정책과 법령으로 확인한다.

## Conditional Safety, Legal, Regulatory and Security Lifecycle

운동·부상·회복·건강정보 또는 사용자 권고에 영향을 주는 웨지는 한 번의 서류 승인이 아니라 다음 생명주기로 검증한다.

| 단계 | 필수 활동 | 종료 증거 |
|---|---|---|
| G3 — 분류·설계 | 대상 연령·취약 사용자와 제외 기준, 의도된 사용 목적·금지 표현, 의료/웰니스·스토어·데이터 규제 분류, 위해·위협·개인정보 영향 모델, 금기·오권고·데이터 오류 시나리오, 접근성 요구, 통제 요구사항과 시험·사고 대응 계획 | 개인정보·보안과 적용 시 법무·규제·안전/임상 책임자가 서명한 분류, 위험대장, 시험 계획. 구현 전이라 실행 결과를 요구하지 않음 |
| G4 — 통제 구현·시험 | 인증·권한·암호화·감사, 백업/복구, 삭제/내보내기, 킬스위치, 잘못된 권고·권한 거부·데이터 오류·공급자 장애·접근성의 양성/음성 시험 실행 | 독립 검증 결과, 결함 심각도, 미해결 고위험 결함 0건, 롤백·삭제·내보내기 실행 증거 |

면책 문구는 위해 통제나 규제 분류를 대신하지 않는다. 해당 책임자가 자격·근거·대체 통제를 포함한 `N/A`를 승인하지 않으면 항목을 생략할 수 없다.

## Test and Verification Strategy

### Design and documentation stage

- `git diff --check`
- 문서가 참조하는 로컬 파일과 상대 링크 존재 확인
- Wiki 수치의 독립 재계산
- 단계·게이트·산출물·통과 조건의 상호 일관성 검토
- 독립 검토자가 완전성, 일관성, 명확성, 범위, 실행 가능성을 평가

### Implementation stage

- 기능별 첫 변경은 실패하는 테스트에서 시작한다.
- 테스트 계층은 선택된 수직 슬라이스와 실제 빌드 구성에 따라 정한다. 존재하지 않는 프레임워크나 명령을 가정하지 않는다.
- Wiki 배포 가이드에 있는 `./gradlew test`, `flutter analyze`, `flutter test`, `npm run build`는 해당 모듈과 설정 파일이 실제로 존재할 때만 사용한다.
- 자동 테스트만으로 확인할 수 없는 Health Connect, 백그라운드, 오프라인 복구와 배포 동작은 승인된 실기기 또는 실제 환경에서 검증한다.
- 모든 성공 보고에는 명령, 환경, 시각, 결과와 미검증 범위를 남긴다.

## Distribution Plan

### Program documents

설계·계획은 작업 브랜치에서 검토 후 승인된 통합 절차로 `develop`에 반영한다. GitHub Wiki에 필요한 내용은 `wiki/` 게시 저장소에 별도 동기화한다. 현재 문서는 커밋·푸시 정책을 새로 승인하지 않는다.

### Product

제품 형태와 배포 방식은 아직 확인되지 않았다. G3에서 선택된 웨지가 모바일 앱인지, 웹 서비스인지, 트레이너 도구인지부터 확정하고 사용자 기기 소유 형태, 조직 보안 정책과 업데이트 통제 요구에 맞는 채널을 선택한다. 다음 채널은 서로 바꿔 부르지 않는다.

| 채널 후보 | 이 프로그램에서의 의미 | G3에서 확인할 사항 |
|---|---|---|
| Managed Google Play private app | 조직의 관리형 Google Play를 통해 허용된 조직 사용자에게만 배포 | EMM·조직 계정·대상 사용자, 당시 Health declaration 예외와 조직 정책 |
| Play internal app sharing | 지정 테스터에게 임시 빌드 링크를 제공하는 개발 시험 수단 | 만료·서명·접근 대상과 프로덕션 파일럿 사용 가능 여부 |
| Play internal testing | 개발자 계정의 제한된 내부 테스트 트랙 | 계정·테스터 자격, 심사·정책 적용 범위, 승격 절차 |
| Play closed testing | 정의된 외부/내부 테스터 그룹의 사전 출시 트랙 | 모집·동의·국가·심사·데이터 정책과 프로덕션 전환 |
| Play public listed release | 스토어 검색·목록을 통한 공개 배포 | Health apps declaration, 데이터 안전성, 개인정보처리방침, 조직 계정과 심사 자료 |
| Play unlisted release | 직접 링크로 발견하지만 Play를 통해 배포되는 릴리스 | “비공개 조직 앱”으로 간주하지 않고 당시 전체 정책 적용 여부 확인 |
| Play 외 직접·기업 배포 | 조직이 APK·MDM 등 별도 수단으로 기기와 업데이트를 통제 | 사이드로드 정책, 서명·업데이트·회수·기기 보안·지원 책임 |

G3 결정문에는 채널의 정확한 공식 명칭, 국가, 계정 유형, 사용자 자격, 공개성, 프로덕션 여부, 당시 공식 정책 링크·확인일과 승인자를 기록한다. 공개 여부나 테스트 트랙 이름만으로 Health Connect 신고 예외를 추론하지 않는다. 공개 Google Play와 Health Connect를 함께 선택하면 당시의 Health apps declaration, 데이터 안전성, 개인정보처리방침, 데이터 타입별 필요성, 개발자 계정 유형과 심사 자료를 출시 체크리스트에 포함한다. 관리형 비공개 배포를 선택하면 공식 예외 범위와 조직 정책을 다시 확인해 기록한다.

CI/CD는 실제 소스 저장소와 빌드 구성이 확인된 뒤 다음 능력을 제공해야 한다.

- 테스트 실패 시 패키징과 배포 차단
- 환경별 비밀 분리
- 추적 가능한 버전과 배포 승인 기록
- 제한 파일럿 대상 통제
- 이전 검증 버전으로의 롤백

## Success Criteria

프로그램 성공은 기능 수나 문서 수가 아니라 다음 증거 사슬의 완성으로 판단한다.

| 단계 | 측정 가능한 성공 |
|---|---|
| G-1 | 한시 위임, 발견 자원, 임시 역할과 전문 검토 조달 경로가 이름·기한과 함께 기록됨 |
| G0A | 고정 말뭉치, 문서 권위, 알려진 충돌, 발견 안전 경계와 소유자가 기록됨 |
| G1 | 명시된 사용자·경제적 후원자·현재 업무·기준선·실패·전환 이유·현재 비용과 예산 경로가 증거 ID와 연결됨 |
| G2A | 사전 등록한 핵심 업무를 무안내로 완료·복구하고 미해결 U1/U2 없이 독립 공동 승인을 받음 |
| G2B | 사전 등록한 기준으로 전후 결과, 반복 선택, 제안 조건에 대한 실제 약정과 초기 경제성을 기록함 |
| G0B | 웨지에 영향 주는 요구사항·데이터·테스트·배포 문서가 추적 가능하고 충돌 없음 |
| G3 | 규제·안전·보안·경제성·실제 저장소·환경·배포와 첫 실패 테스트가 승인됨 |
| G4 | 수직 슬라이스 테스트가 통제 환경에서 통과하고 G2 결과를 재현함 |
| G5 | 제한 운영 파일럿이 사전 목표, 리텐션·경제성·운영 한계를 충족하고 고위험 사건 종료와 삭제·내보내기를 검증함 |
| G6 | 각 추가 기능이 별도 수요·위험·운영 증거를 통과함 |

현재 기준선이 없으므로 이 문서는 임의의 리텐션, 시간 절감 또는 실패율 목표를 제품 성공 수치로 확정하지 않는다. G1에서 측정 방법과 기준선을 먼저 고정한다.

## Dependencies

- 실제 후보 사용자와 업무 관찰 접근
- `GO/STOP` 권한과 문제 비용·예산 책임이 있는 경제적 내부 후원자
- Wiki 문서와 범위를 소유할 사람
- 작업로그가 가리키는 실제 소스 또는 해당 작업이 없다는 확인
- 게이트마다 이름이 배정된 책임자·필수 검토자·승인자·거부권자
- 식별 가능한 연구 원자료를 Git 밖에 보관·삭제할 승인 시스템
- 선택된 웨지에 필요한 기기, 계정, 환경과 개인정보·보안·법무·규제 승인
- 경쟁 대안, 리텐션과 지불 행동을 측정할 수 있는 참여자·기간
- 실제 모델·토큰·호출·가격·수수료에 기반한 단위 경제 입력값
- 구현 착수 전 실제 빌드·테스트·배포 구성
- 커뮤니티 착수 전 운영 책임자

## The Assignment

제품 작업 전에 다음 한 묶음의 현장 증거를 만든다.

**데모 없이 이름이 확인된 후보 사용자 한 명이 현재 업무를 수행하는 장면을 직접 관찰하고, 이름이 확인된 후원자 한 명에게 기준선·목표·`GO/STOP` 권한을 명시하게 한다. 식별 가능한 원자료와 동의는 승인된 Git 외부 저장소에 두고, 관찰한 단계·사용 도구·소요 시간·실패 결과의 편집 요약과 증거 ID만 `docs/discovery/`에 남긴다.**

이 과제는 G1의 첫 증거 묶음일 뿐, 최소 2명·총 3회 관찰과 나머지 통과 조건을 대신하지 않는다.

관찰 전에는 새 기능 우선순위나 구현 일정을 확정하지 않는다.

## Appendix A — What I Noticed About How You Think (Non-normative)

이 절은 제품·게이트 요구사항이 아니며 승인 범위를 만들지 않는다.

- “추측·예상 금지”를 최상위 규칙으로 지정했다. 따라서 이 설계는 Wiki의 숫자와 진행 표시를 사실로 승계하지 않고, 파일과 명령으로 확인 가능한 항목만 현재 상태로 기록한다.
- “테스트 코드 우선”과 “항상 엄격하게 검증·테스트”를 요구했다. 이에 따라 각 단계는 결과 주장보다 통과 증거와 중단 조건을 먼저 정의한다.
- “모든 설계/계획 문서는 하위 `docs` 폴더”라는 경계를 지정했다. 그래서 이 설계와 이후 증거·결정·검증 산출물은 역할별 `docs/` 경로를 사용한다.
- 권장안 A 대신 C를 선택했다. 장기 기능을 확정하지 않으면서도 단계별 프로그램 구조를 유지하고, 이미 승인한 수요 부재 전제를 무시하지 않도록 C 내부에 A와 B의 검증 단계를 의무 게이트로 포함했다.
