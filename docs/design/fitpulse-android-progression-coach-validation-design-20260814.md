## 최종 결정

FitPulse의 범용 “AI 운동·건강 올인원 앱” 개발은 진행하지 않는다. 검증할 제품 가설을 다음 하나로 좁힌다.

> **기존 운동 기록을 가져와 지난 수행과 RPE를 바탕으로 다음 중량·횟수를 제안하고, 선택적으로 회복 추이를 근거에 포함하며, 오프라인에서도 기록을 잃지 않는 Android 근력운동 코치**

이 문서가 승인하는 것은 위 가설의 **문제·사용성·반복 사용·결제 검증**이다. 다음 항목은 승인하지 않는다.

- 현재 저장소 상태에서 14주 안에 상용 베타를 만들 수 있다는 주장
- `FitPulse` 이름으로 브랜드 투자를 시작하는 것
- Health Connect, LLM, 서버와 구독을 처음부터 모두 구현하는 것
- 인터뷰 의향을 시장 수요 또는 매출로 간주하는 것
- 내부 목표치를 업계 표준이나 성공 보장 수치로 사용하는 것

14주는 정식 출시 약속이 아니라 **단계별 검증 예산 상한 후보**다. 각 게이트가 `GO`일 때만 다음 단계로 이동하며, 구현 저장소·인력·기기·계정·규제 경로가 확인되기 전에는 일정 확정을 금지한다.

## Evidence Labels

- **확인됨**: 저장소 파일, 실행한 명령 또는 사용자의 명시적 결정으로 확인
- **외부 근거**: 확인일에 공식 문서·1차 자료 또는 명시된 상업 자료에서 확인
- **회사 주장**: 경쟁사가 자사 페이지나 스토어 설명에서 공개했지만 외부 감사되지 않음
- **내부 실험 가설**: FitPulse가 시험할 가격·수치·세그먼트·기능 가설이며 업계 표준이 아님
- **미확인**: 실제 사용자 행동, 구현물, 조직 자원 또는 담당자 증거가 없음
- **차단**: 해결 전에는 해당 개발·배포·판정을 진행할 수 없음

## 확인된 현재 상태

### Repository

- **확인됨:** 등록된 표준 소스 확장자와 일반 빌드 설정을 검색했지만 애플리케이션 구현과 실행 가능한 빌드 구성을 찾지 못했다.
- **확인됨:** `gradlew`, Gradle 설정, `pubspec.yaml`, `package.json`, Docker Compose 파일이 현재 루트 저장소에 없다.
- **한계:** 비표준 확장자나 외부 저장소의 구현 부재까지 증명하지 않는다.
- **결론:** Wiki의 Flutter·Spring Boot·Health Connect·오프라인 동기화 설계는 구현 증거가 아니다. 현재 단계에서 기술적으로 주장할 수 있는 것은 설계 후보와 검증 경로까지다.

### Demand

- **확인됨:** 실제 대상 사용자 관찰, 반복 문제의 기준선, 기존 앱에서 전환한 행동, 사전 결제 또는 유지율 코호트는 아직 없다.
- **외부 근거:** 운동 앱 시장과 유료 구독 사례는 존재한다.
- **결론:** 시장 존재는 확인됐지만 이 제품의 수요는 미확인이다.

## 문제와 고객 가설

### 후보 사용자

다음 조건을 모두 또는 대부분 만족하는 사람을 첫 인터뷰 모집 기준으로 사용한다.

- 한국 거주, Android 또는 Galaxy Watch 사용자
- 근력운동 경력 6개월~3년, 주 3~5회 운동
- 메모·스프레드시트·기존 운동 앱에 3개월 이상의 기록이 있음
- 다음 운동의 중량·반복·세트 수를 스스로 결정함
- 수면·심박·체중 데이터가 있어도 훈련 조정에는 일관되게 활용하지 못함

이 목록은 **모집 필터**이지 고객 확정 사실이 아니다. 경력 구간, 운동 빈도 또는 기기 조건이 실제 문제와 상관없으면 G1 결과에 따라 바꾼다.

### 해결할 작업

사용자가 운동 전후에 반복하는 한 작업을 검증한다.

> “이전 수행을 확인하고 오늘의 중량·횟수·세트 수를 정한 뒤, 수행 결과를 다음 계획에 반영한다.”

검증할 손실은 다음과 같다.

- 다음 목표를 결정하는 데 걸리는 시간과 불확실성
- 목표를 지나치게 높이거나 낮게 잡아 생기는 실패·정체·불필요한 수정
- 기존 기록을 옮기지 못해 앱 전환을 포기하는 행동
- 네트워크·앱 종료 때문에 기록이 유실되거나 중복되는 사건

인터뷰에서 “불편하다”는 발언만 수집하지 않는다. 실제 기록, 최근 세 번의 의사결정, 사용 도구, 소요 시간, 수정 횟수와 실패 사례를 관찰한다.

### 피할 초기 사용자와 주장

- 운동을 처음 시작하는 전체 초보자
- 식단·다이어트·홈트·러닝을 한 앱에서 원하는 대중
- 질환 관리, 통증 치료, 부상 재활을 목적으로 하는 사용자
- 세부 프로그램을 직접 설계하는 최상급 선수
- “정상/비정상”, “과훈련”, “부상 가능성”, “의학적으로 안전” 같은 의료·안전 판정

## 제품 포지셔닝 가설

### 사용자 메시지

주 메시지 후보:

> **오늘 몇 kg을 들어야 할지 근거와 함께 알려주는 근력운동 코치**

보조 메시지 후보:

> 지난 수행과 RPE를 바탕으로 다음 중량·횟수를 제안합니다. 승인된 경우에만 수면·안정 심박 추이를 참고하며, 인터넷이 끊겨도 기록은 로컬에 먼저 저장됩니다.

Spring Boot, Change Token, Operation Queue, JSON Schema와 LLM 공급자는 마케팅 첫 화면에 쓰지 않는다.

### 차별화 가설

플랜핏과 Fitbod도 자동 진행을 주장하므로 기능 존재만 비교하지 않는다. 다음 조합이 실제 전환 행동을 만드는지 시험한다.

1. **이동 가능성:** 기존 기록 가져오기, 사전 미리보기, 운동명 매핑, 되돌리기와 항상 가능한 내보내기
2. **설명 가능한 진행:** 증량·유지·감량 이유, 사용 데이터, 신뢰 부족 시 “제안 없음” 표시
3. **사용자 통제:** 한 번에 수락·수정·거부하고 수정 이유를 선택적으로 기록
4. **한국 운동 환경:** 실제 헬스장의 원판·덤벨·머신 증량 단위와 kg 중심 입력
5. **기록 신뢰:** 로컬 우선 저장, 앱 종료 복구, 재연결 동기화, 충돌·중복의 가시적 해결
6. **회복의 제한적 역할:** 회복 데이터가 계획 전체를 자동 결정하지 않고 사용자가 확인 가능한 조정 근거로만 작동

## Approaches Considered

### Approach A — 범용 AI 건강·운동 앱

운동 기록, 식단, 수면, 체중, 소셜, 챌린지와 AI 채팅을 함께 만든다. Wiki 기능군을 가장 많이 보존하지만 플랜핏·번핏·Hevy·Fitbod와 직접 경쟁하고, 어떤 결과가 전환·결제를 만들었는지 분리해 검증하기 어렵다. **거절됨.**

### Approach B — 회복 데이터 자동 코치부터 시작

Health Connect의 수면·심박·체중을 처음부터 자동 진행에 결합한다. 장기 방향과 가깝지만 기본 진행 제안보다 먼저 권한·개인정보·규제·실기기 동기화 위험을 부담하며, 회복 데이터의 추가 가치가 아직 확인되지 않았다. **조건부 후속 후보.**

### Approach C — 기본 진행 우선, 회복은 증거 후 추가

기존 기록 이동, 로컬 우선 기록과 이전 수행+RPE 규칙으로 다음 운동 결정 문제를 먼저 검증한다. 회복 데이터는 기본 가치, 필요성, 제품 분류와 개인정보 통제를 통과한 경우에만 별도 어댑터로 추가한다. **선택됨.**

선택 이유는 기능을 덜 만드는 데 있지 않다. 지불 결과를 다른 위험과 분리해 더 빨리 반증할 수 있고, Health Connect가 제외돼도 핵심 사용자 작업이 남기 때문이다.

## 최소 제품 범위

### 반드시 검증할 능력

#### 1. 데이터 이동

- CSV 템플릿과 샘플
- 운동명·단위·날짜 매핑 미리보기
- 모호하거나 알 수 없는 운동의 사용자 확인
- 중복 감지와 가져오기 전체 되돌리기
- 전체 CSV·JSON 내보내기와 계정 삭제

내보내기와 삭제는 유료 기능으로 막지 않는다.

#### 2. 빠른 로컬 우선 기록

- 이전 중량·횟수 즉시 불러오기
- 한 손 조작, 세트 복사, 워밍업·슈퍼세트·드롭세트
- kg/lb 변환 시 원본 단위와 반올림 기록
- 로컬 영속 저장 후 화면 성공 표시
- 앱 강제 종료 후 미완료 세션 복구
- 재연결 시 멱등 동기화와 충돌의 사용자 가시성

“10초 이내 기록”은 내부 사용성 목표 후보다. G2A에서 시작·종료 상태와 기기 조건을 정한 뒤 측정한다.

#### 3. 자동 진행 제안

- 이전 수행, 목표 반복 범위와 RPE로 `증량 / 유지 / 감량 / 제안 없음` 중 하나를 산출
- 실제 사용 가능한 증량 단위로 반올림
- 제안에 사용한 기록과 규칙을 표시
- 사용자가 제안을 항상 수정하거나 거부할 수 있음
- 제안 수락·수정·거부와 다음 수행 결과를 연결해 측정

첫 가치 검증에서는 결정 규칙과 계산 결과를 재현할 수 있어야 한다. 수치 결정에 LLM을 사용할지는 G3에서 **결정 규칙 엔진**, **규칙+LLM 설명**, **검증형 LLM**을 같은 데이터셋으로 비교한 뒤 정한다.

#### 4. 회복 참고 정보 — 조건부

- 최소 후보: 수면 시간 추이, 안정 심박 추이, 최근 훈련 빈도·볼륨, 체중 변화
- 개인의 최근 기준선과 비교하고 모집단의 정상 범위를 판정하지 않음
- 데이터 없음·권한 거부·오래된 데이터에서는 기본 진행 제안으로 복귀
- 어떤 데이터가 어떤 조정에 영향을 줬는지 표시
- 회복 데이터에 따른 조정은 별도 스위치로 끌 수 있음

Health Connect가 없어도 기본 진행 제안의 가치를 검증할 수 있어야 한다. 회복 데이터가 실제로 수락률·결과·유지율을 개선하지 못하면 초기 제품에서 제외한다.

#### 5. 주간 조정 요약

- 지난주 대비 부위별 세트 변화
- 최근 목표 반복 달성 여부
- 다음 운동의 증량·유지·감량 후보
- 사용한 데이터와 제외된 데이터
- 의학적 진단·치료가 아니라는 범위 안내

### NOT in scope

- 식단 기록과 음식 사진 분석
- 소셜 피드, 챌린지, 뱃지와 실시간 랭킹
- 트레이너 마켓과 B2B2C 대시보드
- 부상·재활 처방과 질환 관리
- 범용 건강 점수와 SpO2 기반 판정
- AI 채팅봇
- 상세 React 관리자
- iOS 정식 앱
- 평생 이용권
- 공개 대규모 광고 집행

위 항목은 이번 문서에서 후속 일정도 약속하지 않는다. 선택된 웨지의 유료 유지가 검증된 뒤 각각 새 미니 게이트로 평가한다.

### 사용자 가치 흐름

```text
기존 기록 가져오기

        ▼
지난 수행 확인 ──▶ 오늘 제안과 근거 확인 ──▶ 수락·수정·거부

        │                                      ▼
전체 내보내기 ◀── 다음 제안 갱신 ◀── 로컬 우선 세트 기록
                                               │
                                               ▼

```

### 제안 데이터 흐름

```text
이전 수행 + 목표 반복 + RPE
          │
          ├── nil/부족 ───────────────▶ 제안 없음 + 필요한 입력 표시
          │
          ▼
재현 가능한 진행 규칙
          │
          ├── 계산 불가/위험 경계 ───▶ 유지 또는 제안 없음
          │
          ▼
사용 장비 증량 단위 적용
          │
          ├── 회복 사용 OFF/데이터 없음 ─┐
          │                               │
          └── 회복 사용 ON ─▶ 추이 검증 ─┤
                                          ▼
                             제안 + 근거 + 사용 데이터
                                          │
                         수락 ───── 수정 ─┴─ 거부
                           │          │        │
                           └──────────┴────────┘
                                      ▼
                            실제 수행 결과와 연결
```

### 기록 동기화 상태

```text
DRAFT ──로컬 저장 성공──▶ PERSISTED ──큐 등록──▶ PENDING_SYNC
  │                           │                       │
  └─저장 실패▶ WRITE_FAILED   │                       ├─성공▶ SYNCED
                              │                       ├─충돌▶ CONFLICT
                              │                       └─재시도▶ PENDING_SYNC
                              └─앱 종료/재실행──▶ RECOVERED

금지 전이:
- DRAFT → SYNCED: 로컬 영속 저장을 건너뛸 수 없음
- WRITE_FAILED → 성공 표시: 사용자에게 저장 실패를 숨길 수 없음
- CONFLICT → SYNCED: 정책 또는 사용자 결정 없이 덮어쓸 수 없음
```

**STOP 조건:** 구별 가능한 후보 이름 또는 연구 데이터를 합법적으로 보관할 경로가 없다.

### Gate V1 — 문제 검증

**내부 실험 설계 후보**

- 모집 목표: 조건에 맞는 30명
- 행동 증거: 최근 운동 기록과 최근 세 번의 다음 목표 결정 과정을 직접 검토
- 비교 대상: 실제 사용 중인 플랜핏·번핏·Hevy·Strong·메모·스프레드시트
- 제안 노출 전 현재 방식, 시간, 실패와 전환하지 않는 이유 기록

**내부 GO 기준 후보**

- 10명 이상이 다음 중량·반복 결정 문제를 독립적으로 반복 제시
- 10명 이상이 보유한 회복 데이터를 훈련 조정에 일관되게 쓰지 못함
- 5명 이상이 정의된 범위·기간·가격에 대해 환불 가능한 예약금, 유료 파일럿 또는 동등한 실제 약정 행동을 완료
- 최소 5개의 실제 내보내기 파일 또는 익명화된 기록 형식을 확보해 가져오기 난이도를 확인

30·10·5는 업계 표준이 아니라 과도한 단일 인터뷰 확신을 막는 내부 규칙이다. 모집 편향, 중복 응답, 유도 질문과 조건 없는 결제 의향은 통과 증거에서 제외한다.

### Gate V2 — 컨시어지 가치 검증

신규 앱·서버·Health Connect·LLM 없이 사용자의 기존 기록을 승인된 도구로 분석해 다음 운동 제안과 근거를 제공한다.

**측정**

- 제안 확인까지 걸린 시간
- 수락·소폭 수정·거부 비율과 이유
- 목표 반복 달성, 계획 변경과 중단
- 서로 다른 운동 주기에서 자발적으로 다시 요청한 비율
- 약속된 가격의 결제·유지·환불 행동

**GO 조건:** G1에서 사전 등록한 결과·반복 사용·결제 임계값을 모두 충족한다. 결과를 본 뒤 임계값을 낮출 수 없다.

- 실제 가져오기 파일로 미리보기·매핑·되돌리기 사용성 검증
- 로컬 기록, 앱 종료 복구와 충돌 해결 프로토타입 검증
- 진행 규칙의 골든 데이터셋과 안전 경계 승인
- 구현 저장소, 빌드 파일, 담당자, Android 실기기와 배포 계정 확인
- Health Connect 데이터 타입별 필수성, 권한·삭제·동기화 POC
- 식약처에 의도된 사용 목적과 데이터 흐름을 제시해 분류 사전상담
- 개인정보·국외 이전·AI 위탁·스토어 신고·구독 약관 승인
- 실패하는 첫 테스트와 실행할 실제 명령 확정

**차단:** 위 항목을 충족하기 전에는 14주 구현 일정이나 상용 베타 가능성을 승인하지 않는다.

### Gate V4 — 단계형 Android 비공개 베타

베타는 다음 순서로만 확대한다.

```text
내부 실기기 ─▶ 20명 ─▶ 50명 ─▶ 100명 ─▶ 최대 200명
     │           │        │         │
     └──── 각 단계: 데이터 손실·안전·동기화·지원·삭제 검토 ────┘
```

각 단계에서 복구 불가능한 기록 손실, 잘못된 권한 접근, 고위험 권고 또는 삭제 실패가 발생하면 확대를 멈추고 이전 검증 버전으로 롤백한다.

### Gate V5 — 결제 검증

무료 체험 기간과 가격을 고정하지 않고 실제 오퍼로 비교한다.

| 변수 | 실험 후보 | 판정 |
|---|---|---|
| 월간 Pro | 6,900원 | 실제 결제·취소·환불과 공헌이익 |
| 연간 Pro | 49,000원 | 월간 대비 선택률과 갱신 의향, 과도한 할인 여부 |
| 창립회원 첫해 | 39,000원 | 초기 모집 효과와 이후 가격 충격 |
| 무료 체험 | 7일 vs 14일 | 활성화·체험→결제·환불·첫 갱신 |

연 49,000원은 월 6,900원의 12개월 합계보다 약 40.8% 낮고, 39,000원은 약 52.9% 낮다. 할인 폭도 가설로 취급한다.

모든 비율은 분모, 코호트 시작일, 제외 기준, 누락·환불·중도절단 처리와 관찰 기간을 실험 전에 등록한다. 100~200명 모집 자체는 성공 지표가 아니다.

| 로컬 기록·복구 | 승인된 경우 회복 추이와 주간 조정 |
| 가져오기·내보내기·삭제 | 클라우드 백업·다중 기기 |

데이터 이동권과 계정 삭제는 신뢰·법적 처리 기능이므로 무료/유료 여부와 관계없이 제공한다.

### AI 비용 시나리오

Claude Sonnet 5의 2026-08-14 공개 도입 가격에서 입력 6,000토큰·출력 2,000토큰 호출은 다음과 같다.

```text
입력  6,000 × $2 / 1,000,000  = $0.012
출력  2,000 × $10 / 1,000,000 = $0.020
합계                           = $0.032
```

2026-09-01 이후 공개 예정 가격 `$3/$15`에서는 같은 토큰 수가 `$0.048`이다. 위 토큰 수는 계산 예시일 뿐 실제 사용량이 아니다. 월 호출 수와 판정일 환율은 별도 실측·확인한다.

G3에서는 다음 식을 실측 P50·P90·허용 상한에 적용한다.

`월 공헌이익 = 결제액 - 스토어/결제 수수료 - 세금·환불 - 모델 입력·출력·재시도·폴백 - 저장·전송·관측 - 변동 지원비`

AI 비용이 작거나 크다는 결론은 실제 호출 로그와 가격 재확인 전에는 내리지 않는다. 수치 제안을 규칙으로 만들 수 있다면 LLM은 설명·요약에만 쓰는 대안과 반드시 비교한다.

## Test and Verification Strategy

### 현재 문서 단계

- `git diff --check`
- 모든 상대 로컬 링크의 존재 확인
- 외부 수치의 출처·확인일·한계 표기 확인
- `확인됨`, `내부 실험 가설`, `미확인`, `차단` 표현 감사
- 기존 설계와 새 설계의 우선 범위 확인

### 구현 단계 Test-First 계약

```text
가져오기: 실패 파일 테스트 → 미리보기/매핑 → 원자적 반영 → 전체 롤백
기록:     로컬 쓰기 실패 테스트 → 성공 표시 → 앱 종료 → 복구
동기화:   중복/순서역전 테스트 → 멱등 전송 → 충돌 선택
제안:     골든 케이스 실패 테스트 → 최소 규칙 → 경계/단위/제안 없음
회복:     권한 거부/철회/빈 값 테스트 → 기본 진행 폴백
결제:     중복/지연/역전 콜백 테스트 → 권한 원장 → 복원
삭제:     일부 공급자 실패 테스트 → 재시도 → 백업·파생자료 검증
```

각 기능은 단위, 통합, 상태 복구와 실제 Android 기기 테스트를 필요 범위에 맞게 가진다. 실제 빌드 파일을 읽기 전에는 `flutter test`, `./gradlew test` 또는 다른 명령을 실행 가능하다고 보고하지 않는다.

## Performance and Capacity Questions

구현 전 G3에서 다음 상한과 측정 환경을 정한다.

- 한 사용자의 최대 세션·세트·가져오기 행 수
- 로컬 기록 성공 표시 지연 목표와 저사양 Android 기준 기기
- 큐 최대 크기, 재시도 간격과 배터리·데이터 사용 상한
- 동기화 P50/P95/P99와 서버·DB 연결 한계
- 진행 제안 계산 시간과 Health Connect 조회 시간
- 내보내기·삭제의 최대 처리 시간과 진행 표시
- 모델 호출 timeout·동시성·월별 사용자 예산 상한

값을 측정하지 않고 숫자를 채우지 않는다. 부하 시험 데이터에는 실제 건강정보를 사용하지 않는다.

## Observability

민감 원문을 보내지 않는 다음 제품·품질 이벤트를 후보로 둔다.

- `import_started/completed/rolled_back`, 행 수 구간과 오류 코드
- `set_local_write_succeeded/failed`, 지연 구간과 저장소 상태
- `session_recovered`, 복구된 세트 수 구간
- `sync_succeeded/retried/conflicted`, 큐 길이 구간
- `suggestion_shown/accepted/edited/rejected/unavailable`, 규칙 버전
- `recovery_modifier_applied/skipped`, 사유 코드만 기록
- `trial_started/converted/cancelled/refunded`, 상품 ID와 코호트
- `export_completed`, `deletion_requested/completed/failed`

운동명, 자유 메모, 원시 심박·수면 값, 이메일과 이름은 기본 분석 이벤트에서 제외한다. 데이터 손실·권한 우회·잘못된 고위험 제안·삭제 실패에는 경보, 책임자와 런북이 필요하다.

## UX Hierarchy and Accessibility

운동 직전 화면의 정보 순서는 다음으로 고정한다.

1. 직전 수행 중량·횟수와 오늘 제안
2. `증량 / 유지 / 감량 / 제안 없음` 상태와 한 줄 근거
3. 수락·수정·거부
4. 펼쳤을 때만 세부 계산과 선택적 회복 근거

운동 중에는 현재 세트와 다음 입력을 먼저 보이고 차트·주간 리포트·구독 홍보를 노출하지 않는다. 동기화는 로컬 저장 성공 뒤 보조 상태로 표시하며 세트 기록을 가로막지 않는다.

- 한 손 범위에서 핵심 기록·복사·완료 동작을 수행할 수 있어야 한다.
- TalkBack 레이블, 글자 확대, 현재 Android 접근성 지침의 터치 영역과 대비를 실제 기기에서 검증한다.
- 증량·감량·오류를 색만으로 구분하지 않고 텍스트·아이콘·접근성 설명을 함께 제공한다.
- kg/lb와 소수점은 화면 표시와 접근성 읽기 모두에서 단위를 생략하지 않는다.
- 위험 경계를 넘는 수정은 변경 전후 값과 단위를 다시 확인하게 하되 정상적인 세트 기록에는 반복 확인을 요구하지 않는다.
- 로딩·진동·애니메이션만으로 상태를 전달하지 않으며, 시스템의 모션 감소와 글자 크기 설정을 존중한다.

| 진행 제안 | 규칙 계산 중 | 기록 부족과 필요한 입력 | 계산·정책 오류, 제안 없음 | 값·근거·규칙 버전 | 회복 데이터만 제외하고 기본 제안 |
| Health Connect | 권한·데이터 조회 중 | 데이터 없음 | 거부·철회·SDK 오류 | 사용한 추이와 시각 | 일부 타입만 유효하면 사용 범위 표시 |
| 구독 | 스토어 상태 확인 중 | 구매 내역 없음 | 지연·취소·복원 실패 | 상품·갱신일·권한 | 확인 지연 동안 grace 상태 |
| 삭제 | 범위 확인·처리 진행 | 삭제 대상 없음 | 실패한 공급자·재시도 상태 | 삭제 증명과 종료 | 운영본 완료·백업 전파 대기 |

모든 비동기 동작은 중복 탭, 화면 이탈, 앱 종료, 느린 네트워크, 재시도 중 재시도와 오래된 화면 상태를 시험한다. 로딩 화면은 로컬 기록을 막지 않으며, 부분 성공을 전체 성공으로 표시하지 않는다.

## Code Quality Constraints

- 진행 계산은 동일 입력·규칙 버전에서 동일 결과를 내는 순수한 도메인 경계로 둔다.
- UI, 로컬 저장소, 동기화, Health Connect, 결제와 LLM을 어댑터 경계로 분리해 기본 진행 규칙이 외부 장애에 종속되지 않게 한다.
- 시간, 단위 변환, 장비 증량 정책과 규칙 버전을 명시적으로 주입해 테스트가 시스템 시각·지역 설정·난수에 의존하지 않게 한다.
- `catch all`로 계속 진행하지 않는다. Error & Rescue Registry의 구체 오류로 변환하고 사용자 상태·로그·재시도 정책을 함께 정의한다.
- 기록·동기화·결제·삭제 상태 전이는 단일 권위 원장에서 관리한다. 같은 판정 로직을 화면·백그라운드 작업·서버에 복제하지 않는다.
- 스키마·규칙 변경은 버전과 마이그레이션, 이전 버전 읽기, 롤백 시험을 가진다.
- 실제 구현 저장소의 기존 구조를 읽기 전에는 클래스명·패키지·프레임워크를 확정하지 않는다.

## Deployment and Rollback

### 배포 순서

```text
테스트·규제·개인정보 승인
          ▼
내부 실기기 빌드
          ▼
데이터 내보내기·삭제·킬스위치 실행 검증
          ▼
20명 closed cohort
          ▼
단계 종료 검토 ──GO──▶ 다음 코호트
          └─LOOP/STOP▶ 기능 OFF + 이전 검증 버전 + 데이터 보존/삭제 결정
```

### 롤백 원칙

- 진행 제안과 회복 조정은 서로 독립된 기능 플래그를 가진다.
- 회복 조정을 꺼도 기본 기록과 데이터 내보내기는 동작해야 한다.
- 서버 장애가 로컬 기록을 막아서는 안 된다.
- 스키마 변경은 이전 앱 버전의 읽기·동기화와 공존 기간을 가진다.
- 롤백 후 큐 데이터의 재처리·격리·폐기 중 무엇을 할지 버전별 런북에 명시한다.

## 14주 예산 상한 후보

이 표는 날짜 약속이 아니라 게이트별 작업 순서다. 앞 게이트가 실패하면 남은 주차를 기능 개발에 자동 전환하지 않는다.

| 기간 후보 | 허용 작업 | 산출물 | 다음 단계 차단 |
|---|---|---|---|
| 1~2주 | 브랜드·문제·기록 이전 조사 | 후보명 검색 기록, 인터뷰 원칙, 실제 기록 형식 | 반복 문제·약정 없음 |
| 3~4주 | 컨시어지 진행 제안·가격 오퍼 | 규칙 초안, 제안 결과·반복 사용·결제 행동 | 결과·반복·결제 기준 미달 |
| 5~8주 | G3 통과 시 기록·가져오기·기본 진행 수직 슬라이스 | 실패 테스트, 로컬 기록·복구, 가져오기·제안 | 구현 저장소·테스트·안전 미승인 |
| 9~11주 | 기본 가치가 확인된 경우만 Health Connect POC와 조건부 조정 | 실기기 권한·삭제·동기화, 분류 상담 기록 | 필요성·분류·개인정보 미승인 |
| 12~14주 | 준비 기준을 통과한 경우만 20→50명 비공개 베타와 결제 실험 | 코호트 지표, 사건·환불·삭제·롤백 기록 | 고위험 사건, 데이터 손실, 미성숙 코호트 |

100~200명 확대, 고객지원 체계, 공개 출시와 iOS POC는 14주 안에 자동 포함되지 않는다.
