# FitPulse 랜딩 데이터 삭제·보존 런북

Status: ACTIVE — OWNER-ONLY PREVIEW

Updated: 2026-08-14

Owner: 개인사업자 본인

## 목적과 범위

이 런북은 사전검증 랜딩의 `waitlist_entries`, `survey_responses`, `landing_events`, `request_rate_limits`에만 적용한다. 정식 계정, 결제, 건강정보 또는 웨어러블 데이터에는 적용하지 않는다.

현재 배포본은 소유자 전용이다. 이메일 확인 공급자, 실제 데이터 처리 위치, 백업 보존·복구 시 삭제 재적용 절차를 확인하기 전에는 외부 공개하거나 이메일을 발송하지 않는다.

## 자동 보존 규칙

| 데이터 | 보존 상한 | 삭제 방식 |
|---|---:|---|
| 확인되지 않은 이메일·동의 | 14일 | 일일 예약 작업 |
| 확인된 이메일·동의 | 365일 또는 철회 시점 | 일일 예약 작업 또는 직접 삭제 |
| 연결 선택 설문 | 365일 또는 대기자 삭제 시점 | 일일 예약 작업 또는 외래키 연쇄 삭제 |
| 비식별 행동 이벤트 | 365일 | 일일 예약 작업 |
| 요청 제한 기록 | 1시간 | 일일 예약 작업 |

예약 작업은 매일 실행되며 실패 시 다음 실행에서 다시 시도한다. 이메일 확인 자동화가 연결되기 전에는 모든 대기자 행의 `verified_at`이 비어 있으므로 14일 규칙이 적용된다.

## 같은 브라우저에서 직접 삭제

1. 등록 완료 화면에서 **등록 취소 및 데이터 삭제**를 선택한다.
2. 브라우저는 HttpOnly 관리 세션 쿠키와 함께 `DELETE /api/waitlist`를 호출한다.
3. 서버는 관리 토큰 해시가 일치하는 이메일 행을 삭제한다.
4. D1 외래키 `ON DELETE CASCADE`가 연결 설문을 함께 삭제한다.
5. 서버는 관리 세션 쿠키를 만료시키고 항상 일반화된 `202` 응답을 반환한다.

행동 이벤트에는 이메일을 넣지 않는다. 이메일과 연결되지 않은 집계 이벤트는 직접 삭제 대상이 아니며 365일 규칙으로 만료된다.

## 브라우저 정보를 잃은 요청

1. 개인정보 안내에 표시된 문의 주소에서 요청을 접수한다.
2. 회신 확인을 통해 요청자가 대상 이메일을 통제하는지 확인한다. 확인되지 않으면 삭제 실행이나 존재 여부 확인을 하지 않는다.
3. 공급자 콘솔의 매개변수화된 쿼리 기능으로 `lower(email)`이 대상과 일치하는 행 하나만 찾는다. 이메일을 셸 명령, Git, 이슈 또는 작업 로그에 복사하지 않는다.
4. 트랜잭션 안에서 대상 `waitlist_entries` 행을 삭제한다. 연결 설문은 외래키로 함께 삭제된다.
5. 같은 매개변수로 이메일 행과 연결 설문이 0건인지 다시 확인한다.
6. 요청자에게 완료 사실만 알린다. Git에는 이메일 대신 불투명 요청 ID, 처리 시각, 결과와 검산 상태만 기록한다.

일치 행이 없더라도 존재 여부를 공개하지 않고 동일한 완료 안내를 사용한다.

## 일일 검산

다음 항목을 개인식별자 없이 확인한다.

- 예약 작업의 성공 여부와 마지막 실행 시각
- `verified_at IS NULL`이면서 생성 후 14일이 지난 행 수가 0인지
- 생성 후 365일이 지난 대기자·설문·이벤트 행 수가 0인지
- 1시간이 지난 요청 제한 행 수가 0인지
- 외래키 검사가 활성화되어 있고 고아 설문 행이 0인지

검산 결과에는 행 수와 시각만 남기며 이메일, 쿠키, 관리 토큰 또는 IP 주소를 남기지 않는다.

## 실패 대응

예약 작업이나 직접 삭제가 실패하면 외부 공개와 신규 모집을 계속 중지한다. 쓰기 경로를 소유자 전용으로 유지하고, 실패 범위와 최초 시각을 기록한 뒤 원인을 수정하고 동일한 합성 데이터 삭제 시험을 재실행한다. 운영 데이터가 남아 있을 수 있는 동안 완료로 표시하지 않는다.

Cloudflare D1 백업·Time Travel에서 개별 행 삭제가 언제 전파되는지는 현재 확인되지 않았다. 실제 보존 기간, 복구 권한과 복구 후 삭제 요청 재적용 절차를 공급자 문서와 실제 설정으로 확인해 이 런북에 추가하는 것이 공개 전 차단 조건이다.

## 예약 작업 없이 보존 기간을 지키는 경로 (2026-08-17 추가)

배포 플랫폼(ChatGPT Sites)이 **예약 작업(cron)을 지원하지 않는다.** `landing/worker/index.ts`의 `scheduled` 핸들러와 `"crons": ["17 3 * * *"]` 선언은 그대로 두었으나, 프로덕션에서 실행된다는 보장이 없다. 근거는 `docs/verification/fitpulse-landing-platform-data-handling-20260817.md` 항목 7이다.

이에 따라 삭제 경로를 두 개 더 두었다. 셋 중 하나라도 동작하면 보존 기간이 지켜진다.

| 경로 | 트리거 | 실행 조건 | 한계 |
|---|---|---|---|
| 1. 예약 작업 | 플랫폼 cron | 플랫폼이 지원할 때만 | **지원 여부 미확인** |
| 2. 요청 시점 정리 | 쓰기 요청 처리 후 | 마지막 정리 후 **6시간** 경과 | **트래픽이 없으면 실행되지 않음** |
| 3. 외부 스케줄러 | GitHub Actions 일 1회 | 시크릿 설정 + 외부 접근 가능 | 소유자 전용 상태에서는 호출 실패 |

### 경로 2 — 요청 시점 정리

`landing/db/landing-storage.ts`의 `runRetentionPurge()`가 담당한다. 쓰기 요청 처리 후 `ctx.waitUntil()`로 실행되며 응답을 지연시키지 않는다. 실행 시각은 `maintenance_runs` 테이블에 남아 매 요청마다 반복되지 않는다.

**한계가 분명하다**: 방문이 없으면 실행되지 않는다. 등록이 끊긴 뒤 남은 데이터는 이 경로만으로 삭제되지 않는다. 경로 3이 필요한 이유다.

### 경로 3 — 외부 스케줄러

`.github/workflows/retention-purge.yml`이 매일 03:20 UTC에 `POST /api/maintenance/purge`를 호출한다.

필요한 저장소 시크릿:

| 시크릿 | 값 |
|---|---|
| `LANDING_BASE_URL` | 공개된 랜딩 주소 |
| `MAINTENANCE_TOKEN` | Worker에 주입한 것과 같은 토큰 |

**공개 전에는 이 워크플로가 실패하는 것이 정상이다.** 소유자 전용 상태에서는 외부에서 접근할 수 없다.

### 수동 실행

```powershell
curl --request POST `
  --header "Authorization: Bearer <MAINTENANCE_TOKEN>" `
  https://<랜딩 주소>/api/maintenance/purge
```

성공 시 `202 {"accepted":true}`를 반환한다. 토큰이 없거나 틀리면 `401 {"error":"unauthorized"}`다.

**토큰을 질의 문자열로 보내지 않는다.** 접근 로그와 Referer에 남는다. 서버는 질의 문자열 토큰을 인정하지 않는다.

### 토큰 미설정 시 동작

`MAINTENANCE_TOKEN`이 주입되지 않은 환경에서는 정리 엔드포인트가 **모든 요청을 401로 거부한다.** 인증 없는 삭제 트리거를 열어두지 않기 위함이다. 이 경우 경로 2와 3 중 3이 막히므로, 트래픽이 없으면 삭제가 실행되지 않는다.

## 삭제 후 잔존 기간 (2026-08-17 추가)

**저장소에서 행을 지워도 즉시 소멸하지 않는다.**

배포 플랫폼은 삭제 요청 후 **내부적으로 최대 30일** 보관한다고 밝히고 있다(`docs/verification/fitpulse-landing-platform-data-handling-20260817.md` 항목 6). 우리 삭제 API가 D1 행을 지운 뒤에도 그 기간이 지나야 복원 불가 상태가 된다.

WF-01이 기록한 **Cloudflare D1 Time Travel 7일은 우리 계정 기준이며 이 배포에 적용되지 않는다.** 혼동하지 않는다.

개인정보 안내(`landing/app/privacy/page.tsx`)의 "삭제와 문의" 절에 이 사실을 명시했다. 삭제를 "즉시 완료"로 안내하지 않는다.

### 삭제 요청 처리 시 확인 사항

| 확인 | 내용 |
|---|---|
| 대상 행 삭제 | `waitlist_entries`와 연쇄 삭제되는 `survey_responses` |
| 남는 것 | 이메일과 연결되지 않은 `landing_events` 집계 행 |
| 잔존 기간 | 플랫폼 내부 최대 30일 |
| 요청자에게 안내할 것 | 저장소에서 지웠다는 사실과 최대 30일 잔존 |

`landing_events`는 개인식별자를 담지 않으므로 삭제 대상이 아니며 보유기간에 따라 만료된다. 이는 테스트로 강제하고 있다(저장 행에 토큰·이메일 문자열 부재 검산).
