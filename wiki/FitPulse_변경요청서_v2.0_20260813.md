## 1. 변경 관리 프로세스

```
① 변경 요청 접수 (구두 요청도 반드시 문서화)
        ▼
② CR 등록 (CR-xxx 번호 부여, 요청자·영향 범위 기재)
        ▼
③ 영향 분석 (일정 / 비용 / 품질 / 리스크) — 테크리드 담당, 2영업일 내
        ▼
④ 심의 (PO + 테크리드) → 승인 / 조건부 승인 / 보류 / 반려
        ▼
⑤ 승인 시: 관련 문서 갱신(요구사항·설계·API·테스트) → 개발 착수
   반려 시: 사유 기록 후 종료
        ▼
⑥ 반영 확인 및 CR 종료 (Closed)
```

**핵심 원칙**

| # | 원칙 |
|---|------|
| 1 | 구두 변경 요청도 반드시 CR로 문서화한 뒤 승인 절차를 밟는다 |
| 2 | **승인 전까지 개발 작업 미착수** |
| 3 | 영향도는 구체적 수치(일정 일수, 비용 USD)로 제시한다 |
| 4 | MVP 범위 확대 요청은 기본적으로 **후속 백로그로 이관**을 우선 검토한다 |
| 5 | 변경 이력은 버전별로 누적 관리하며 삭제하지 않는다 |

## 변경 배경 및 사유

AI 루틴 추천은 핵심 차별화 기능이나 단일 외부 벤더(Claude API)에 전적으로 의존합니다. 벤더 장애·레이트리밋·타임아웃 발생 시 기능이 완전히 중단되어 사용자 신뢰를 크게 손상시킵니다. 실제 LLM API의 가용성은 100%가 아니므로, 장애 시에도 사용자에게 무언가를 제공할 수 있어야 합니다.

## 변경 전 / 후 비교

| 구분 | 변경 전 | 변경 후 |
|------|---------|---------|
| 요구사항 | Claude API 단일 호출, 실패 시 오류 반환 | 3단 폴백: Claude → OpenAI → 사전 정의 템플릿 |
| 설계 | `AnthropicClient` 직접 호출 | `LlmClientRouter` 도입 + Resilience4j Circuit Breaker |
| API | `status: FAILED` 반환 | `provider`, `fallbackUsed`, 안내 메시지 필드 추가 |
| DB | `ai_model_runs`에 provider 없음 | `provider` 컬럼 추가 (anthropic/openai/template) |

## 영향 범위

| 영역 | 영향 | 관련 문서 |
|------|------|-----------|
| 요구사항 | FR-805, FR-806 신설 / NFR-201 강화 | 요구사항정의서 |
| 설계 | `LlmClientRouter`, `TemplateRoutineProvider` 신설 | 상세설계서 1.3 |
| DB | `ai_model_runs.provider` 추가 (V6 마이그레이션) | ERD 3.15 |

## 6. CR-013 상세 — 커뮤니티 요구사항 복원

### 기본 정보

| 항목 | 내용 |
|------|------|
| CR ID | CR-013 |
| 요청일 | 2026-08-13 |
| 요청자 | PO (문서 검토 중 누락 발견) |
| 유형 | **누락 시정** (신규 요구사항 아님) |
| 긴급도 | 보통 |

### 변경 배경 및 사유

문서 세트 v1.0 작성 시, 원 계획서 v4.0에 명시된 아래 항목이 **문서화 과정에서 누락**되었습니다.

| 원 계획서 위치 | 원문 | v1.0 문서 처리 | 판정 |
|----------------|------|----------------|------|
| 11장 API 설계 (루틴) | `CRUD routines, POST start, GET public, POST like/copy` | `like` 누락, `start`가 표에서 빠짐 | **누락** |
| 2장 기술 스택 | `Redis 7.4 — Refresh Token·캐시·랭킹` | "랭킹" 용도를 뒷받침하는 기능 없음 | **근거 미이행** |
| 4.3 ERD 루틴 | 공개 루틴을 전제로 한 `type` 구분 | `is_public` 컬럼 부재 | **설계 공백** |

작성자(문서 담당)가 "소셜 기능은 V2+ 백로그이므로 좋아요도 제외 대상"으로 판단해 임의 제외했으나, 이는 **CR 절차 없이 범위를 축소한 것**으로 절차 위반입니다. 원 계획서 원문을 기준으로 복원합니다.

### 변경 전 / 후 비교

| 구분 | 변경 전 (문서 v1.0) | 변경 후 (문서 v2.0) |
|------|---------------------|---------------------|
| 요구사항 | FR-306(복사)만 존재 | FR-308~317 신설 (공개·목록·좋아요·랭킹·어뷰징·신고·제재통지) |
| API | `GET /routines/public`만 표기 | publish / public / like / ranking / reports / sanctions 추가 |
| DB | 없음 | routines 확장 6컬럼 + 5테이블 (V9) |
| 인프라 | Redis "랭킹" 문구만 존재 | Redis ZSET 실사용 + 매시 스냅샷 영속화 |
| 안전성 | 없음 | 사전 심사 + 신고 누적 자동 블라인드 + 제재 |

### 영향 분석

| 항목 | 영향 | 산정 근거 |
|------|------|-----------|
| 일정 | **+5일 (A1 트랙)** | 스키마 1일 + 공개·좋아요 2일 + 랭킹 1일 + 신고·블라인드 1일 |
| 비용 | +$0 | 기존 인프라 활용 (Redis 기 도입) |
| 리스크 | **R-16 위험 루틴 유통(P1), R-17 어뷰징(P2) 신규 발생** | 사전 심사·자동 블라인드·제재 체계로 대응 |
| 법적 | 사용자 생성 콘텐츠 유통에 따른 플랫폼 책임 발생 | 신고·차단 수단 제공으로 완화 |

### 결정 사항

- 판정: **승인**
- 조건: ① 공개 전 사전 심사 필수(`ROUTINE_PUBLIC_REVIEW_REQUIRED=true` 기본) ② 신고 누적 자동 블라인드 필수 ③ 심사·제재를 처리할 관리자 도구(CR-014) 없이는 커뮤니티 단독 출시 불가
- 반영 예정: **A1 (15주차)**

> **조건 ③의 의미**: 공개 루틴을 열면 심사·신고 처리 주체가 반드시 필요합니다. CR-013과 CR-014는 독립 승인이 불가능하며, 커뮤니티를 출시하려면 관리자 도구가 선행되거나 동시에 확보되어야 합니다.

## 7. CR-014 상세 — 관리자 기능 상세 확대

### 기본 정보

| 항목 | 내용 |
|------|------|
| CR ID | CR-014 |
| 요청일 | 2026-08-13 |
| 요청자 | PO |
| 유형 | 요구사항 추가 |
| 긴급도 | 보통 |

### 변경 배경 및 사유

원 계획서는 관리자를 후속 백로그의 "React 관리자" 한 줄과 ERD의 `users.role = USER/ADMIN` 컬럼으로만 다뤘습니다. 그 결과 다음 공백이 있었습니다.

| 공백 | 실무상 결과 |
|------|-------------|
| 관리자 API·권한 체계 부재 | 회원 문의·장애 대응 시 **DB 직접 조작**에 의존 → 오조작 위험 |
| 감사 수단 부재 | 누가 언제 어떤 회원 정보를 봤는지 추적 불가 → 개인정보 처리 이력 요구 미충족 |
| 콘텐츠 심사 도구 부재 | CR-013 커뮤니티 운영 자체가 불가능 |
| AI 운영 도구 부재 | 프롬프트 롤백·매핑 검수·비용 통제를 개발자가 수동 SQL로 수행 |
| `users.role` 기반 권한 | 회원 계정 탈취 = 전 회원 데이터 접근 (단일 실패점) |

### 변경 전 / 후 비교

| 구분 | 변경 전 | 변경 후 |
|------|---------|---------|
| 계정 | `users.role='ADMIN'` | **별도 `admins` 테이블 + 별도 토큰 + `/api/v1/admin/**`** (ADR-007) |
| 인증 | 일반 로그인과 동일 | 이메일+비밀번호 → **TOTP 2FA** → 30분 세션(Idle 30분/절대 8h), IP 허용 목록 |
| 인가 | 없음 | **RBAC 5역할 × 27권한**, `@RequirePermission` 강제 |
| 감사 | 없음 | **쓰기 + 민감 조회 100% 기록**, 수정·삭제 불가, 3년 보관 (ADR-008) |
| 개인정보 | 제한 없음 | 기본 마스킹, 해제 시 사유 필수 + 시간당 30회 + 알림 |
