## 1. 프로젝트 개요 및 배경

### 1.1 개요

FitPulse는 **운동 기록의 신뢰성**과 **건강 데이터의 자동 수집**, 그리고 **검증 가능한 AI 루틴 추천**을 하나로 묶은 모바일 중심 피트니스 플랫폼입니다.

- 클라이언트: Flutter 3.47 (Android 우선, iOS는 V1.1)
- 서버: Spring Boot 4.1 모듈러 모놀리스
- 개발 기간: 14주 (MVP)

### 1.2 배경

| 시장 상황 | 설명 |
|-----------|------|
| 홈트·헬스장 기록 앱 시장 성숙 | 기록 앱은 포화 상태이나, **오프라인 안정성**과 **데이터 정합성**이 확보된 제품은 드묾 |
| Google Fit API 지원 종료 흐름 | Android 생태계가 **Health Connect** 중심으로 재편 → 신규 진입 시점 |
| 생성형 AI 대중화 | LLM 기반 루틴 추천이 확산되었으나, **환각(존재하지 않는 운동)·과부하 처방**의 안전성 문제가 미해결 |

## 2. 문제 정의 및 현황 분석

### 2.1 사용자 관점 문제

| # | 문제 | 현황 근거 |
|---|------|-----------|
| P1 | **헬스장 지하·기계실에서 네트워크가 끊기면 기록이 유실됨** | 기존 앱 다수가 단순 임시저장 방식 → 앱 강제 종료 시 세트 기록 소실 |
| P2 | **운동 중 화면 조작이 많아 세트 입력이 번거로움** | 세트 1건 입력에 평균 4~6회 탭 필요 |
| P3 | **건강 데이터(걸음수·심박·수면)를 수기로 옮겨야 함** | 웨어러블 ↔ 기록 앱 간 연동 부재 |
| P4 | **AI 추천 루틴을 신뢰할 수 없음** | 부상 부위 금기 운동 포함, 초보자에게 고급 운동 처방 사례 다수 |

### 2.2 기술 관점 문제

| # | 문제 | 영향 |
|---|------|------|
| T1 | 오프라인 작업의 **순서·의존성**이 보장되지 않음 | 세션보다 세트가 먼저 전송되어 저장 실패 |
| T2 | 재전송 시 **중복 저장** | 총 볼륨·통계 왜곡 |
| T3 | LLM 출력의 **exercise_id 부재** | DB에 없는 운동명 → 저장 불가 또는 쓰레기 데이터 |
| T4 | AI 서비스 장애 시 **기능 전면 중단** | 단일 벤더 의존 |

### 2.3 도입 전 / 후 비교

| 항목 | 도입 전 (기존 방식) | FitPulse 도입 후 | 개선 |
|------|--------------------|------------------|------|
| 오프라인 기록 유실률 | 약 8% (세션 강제 종료 시) | 0% 목표 (Operation Queue 영속화) | **-8%p** |
| 재전송 중복 발생 | 발생 | 0건 (clientId 멱등성) | **완전 제거** |
| 건강 데이터 입력 시간 | 1일 약 2분 (수기) | 0분 (Health Connect 자동) | **-100%** |
| AI 루틴 중 DB 미존재 운동 | 15~30% | 0% (3단계 매핑 + 폐기) | **-100%** |
| AI 장애 시 가용성 | 0% | 100% (Claude→OpenAI→템플릿 폴백) | **+100%p** |
| 세트 기록 응답 P95 | 미측정 | < 200ms (SLA 정의) | **측정·관리 가능** |

```
[기록 유실률]                     [AI 루틴 유효성]
기존  ████████ 8%                 기존  ███████████████ 70~85%
FitPulse □ 0%                     FitPulse ████████████████████ 100%
```

## 3. 제안 솔루션 및 기대 효과

### 3.1 솔루션 4대 축

| 축 | 핵심 솔루션 | 해결 문제 |
|----|------------|-----------|
| ① 운동 기록 안정성 | **Operation Queue** (drift 영속 큐 + 의존성 체인 + server_id 매핑 + 배치 전송 + 충돌 매트릭스 8종) | P1, T1, T2 |
| ② 건강 데이터 자동화 | **Health Connect Change Token** + Background Observer + 90일 fullResync + 배치 500건 분할 | P3 |
| ③ 검증 가능한 AI | **비동기 Job + Fallback 체인 + 3단계 exercise 매핑 + 안전성 검증(부상 금기·볼륨 상한)** | P4, T3, T4 |
| ④ 보안·개인정보 | Google PKCE + Rotational Refresh + secure_storage + 동의 5종 분리 + 30일 유예 삭제 | 앱 심사·PIPA 대응 |

### 3.2 기대 효과

**정량 효과**

| 지표 | 목표치 | 측정 방법 |
|------|--------|-----------|
| 세트 기록 P95 응답시간 | < 200ms | Prometheus `api_response_time_p95` |
| 건강 동기화 성공률 | ≥ 95% | `health_sync_success_rate` |
| AI Job 성공률 | ≥ 90% (폴백 포함 100%) | `ai_job_success_rate` |
| AI 운동 매핑 실패율 | < 10% | `ai_exercise_mapping_failure_rate` |
| 일일 AI 비용 | < $10 | `ai_daily_cost_usd` |
| 오프라인 기록 유실 | 0건 | 통합 테스트 + 실기기 검증 |

**정성 효과**
- 네트워크 품질과 무관하게 "기록이 사라지지 않는 앱"이라는 신뢰 확보
- AI 추천에 **근거와 안전장치**를 부여 → 의료 오인 리스크 회피 ("진단" 표현 금지 정책)
- 모듈러 모놀리스 구조로 향후 MSA 전환 시 모듈 단위 분리 가능
